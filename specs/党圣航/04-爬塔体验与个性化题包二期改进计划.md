# 爬塔体验与个性化题包二期改进计划

## 1. 改进目标

在上一版“动态路线、通关解锁、诊断跳过战斗、能力变化日志”的基础上，继续解决四个体验和真实性问题：

1. 能力图谱要显示真正的能力雷达图，并支持“通关前 vs 通关后”对比。
2. 地图节点加载不能每次都显得像在等 AI 现场生成，路线生成要快、稳定、可展示。
3. 诊断房全对后不再停留等待手动操作，直接进入奖励/结算流程。
4. 战斗房和诊断房的题目必须来自数据库题库，并根据学生画像、掌握度、历史错题、节点难度做个性化推荐，不能每关都是固定几道演示题。

整体原则：

- AI 负责“选择、排序、解释”，不负责前端页面实时造数据。
- 后端负责“校验、落库、缓存、兜底”，保证 AI 慢或不可用时仍然可玩。
- 前端只消费后端生成好的 run、node、questionPack、abilityRadar，不再在组件里临时拼关卡和固定题。

## 2. 当前问题判断

### 2.1 能力图谱还不是雷达对比

当前 `StudentAbilityMapPanel.vue` 已经会读取：

- `getAbilityMap(courseCode)`
- `getKnowledgeGraph(courseCode)`
- `getKnowledgeMastery(studentNo, courseCode)`
- `getAbilityDeltas(studentNo, courseCode)`

但展示仍是卡片列表和最近变化说明，没有像示例图那样把多个能力维度放到雷达坐标里，也没有把“本次通关前”和“本次通关后”两条曲线放在一起对比。

### 2.2 进入地图加载慢

当前路线生成已经由后端持久化，但首次进入时如果没有 active run，会同步执行：

- 读取知识点、能力映射、掌握度。
- 尝试调用 AI 生成路线。
- AI 不可用时再使用规则兜底。
- 写入 run 和 node。

这会导致首次进入页面有明显等待。并且如果 AI 参与生成完整节点布局，速度、稳定性、可控性都不适合展示版本。

### 2.3 诊断全对后的跳转还不够顺滑

当前后端已经支持 `diagnoseNode`，诊断全对可以把诊断节点和绑定战斗节点一起视为通关。但前端体验上还可以更直接：

- 诊断最后一题答完后立即提交后端。
- 后端返回 `battleBypassed=true` 后立即切到奖励/结算，不再显示额外手动入口。
- 奖励结算页展示“诊断全对，战斗已跳过”的明确说明。

### 2.4 题目推荐仍偏前端临时筛选

当前 `DiagnosisRoom.vue` 和 `BattleRoom.vue` 会：

- 优先用任务题 `getTaskQuestions(taskNo)`。
- 否则用 `getQuestionsByKnowledgePoint(courseId, kpId)`。
- 然后前端 `.slice(0, 3)` 或 `.slice(0, roomQuestionLimit)`。
- 如果没有题，则使用组件内 fallback 演示题。

这会导致：

- 同一知识点总是前几道题。
- 无法根据学生水平动态调难度。
- 无法避开最近刚做过的题。
- AI 无法参与题目选择，只能事后诊断。
- 题目推荐逻辑散落在前端组件中，不可持久化、不可复盘。

## 3. 总体方案

### 3.1 路线生成改为“模板库 + AI 选择”

不要让 AI 每次完整生成复杂节点图。提前在后端设计几套完整、可展示、可控的节点模板，由 AI 或规则只选择模板和填充知识点。

模板示例：

- `linear_foundation_5`：5 个主战斗，适合基础薄弱学生。
- `diagnosis_heavy_6`：诊断较多，适合掌握度不稳定学生。
- `branch_supply_7`：战斗后带商店/补给分支，适合中等水平学生。
- `elite_boss_8`：精英战和 Boss 更多，适合高掌握度学生。
- `remedial_short_4`：短路线，适合只补弱点。

AI 输入学生画像后只返回：

```json
{
  "templateId": "diagnosis_heavy_6",
  "focusKnowledgePointIds": ["kp-001", "kp-004", "kp-009"],
  "difficultyBias": "adaptive",
  "reason": "该学生最近在对象编程相关题目波动较大，先诊断再推进。"
}
```

后端再根据模板生成真实 `student_tower_node`，并校验知识点、能力点、解锁关系。

收益：

- 首屏快。
- 布局稳定好看。
- 节点数量仍然不固定。
- AI 仍然参与个性化，但不把页面可用性交给 AI 延迟。

### 3.2 题目推荐改为后端题包

新增 `TowerQuestionPackService`，每个节点进入前由后端生成题包：

```text
student + run + node + mode(diagnosis/battle)
  -> 数据库候选题
  -> 规则打分
  -> AI 可选重排
  -> 后端校验
  -> 持久化 question pack
  -> 前端直接渲染题包
```

前端不再自己 `slice(0, N)`，只调用：

```http
GET /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/question-pack?mode=diagnosis
GET /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/question-pack?mode=battle
```

### 3.3 能力雷达图由后端返回对比数据

新增能力雷达接口：

```http
GET /api/students/{studentId}/ability-radar?course_id={courseCode}&run_id={runId}&node_id={nodeId}
```

返回当前课程能力点维度，以及本次节点通关前后分数：

```json
{
  "mode": "node",
  "runId": "run-001",
  "nodeId": "node-003",
  "dimensions": [
    {
      "abilityPointId": "ap-001",
      "name": "程序设计",
      "beforeScore": 62,
      "afterScore": 70,
      "delta": 8,
      "reason": "本次战斗中循环和函数调用题正确率较高。"
    }
  ],
  "series": {
    "before": [62, 55, 70, 48, 64],
    "after": [70, 58, 72, 48, 66]
  },
  "summary": "本次通关主要提升了程序设计和面向对象建模能力。"
}
```

前端使用已有 `echarts` 画 radar，不需要新增依赖。

### 3.4 诊断全对自动进入奖励结算

诊断房最后一题答完后自动：

1. 生成答题摘要。
2. 调用 `diagnoseTowerNode`。
3. 如果 `battleBypassed=true`，设置 `battleResult`。
4. 跳到 `reward`。
5. 奖励选完后进入 `settlement`。
6. 结算页展示能力雷达变化。

## 4. 数据模型调整

### 4.1 新增路线模板常量，不一定落库

先用 Java 常量类即可：

```text
backend/src/main/java/com/neu/CoursePlatform/service/impl/TowerRouteTemplateCatalog.java
```

结构：

```java
class TowerRouteTemplate {
    String templateId;
    String name;
    List<TowerTemplateNode> nodes;
}

class TowerTemplateNode {
    int row;
    int col;
    String roomType;
    String unlockAfterRef;
    String parentRef;
    int difficultyOffset;
}
```

后续如果教师端需要配置模板，再迁移成数据库表。

### 4.2 新增题包表：`student_tower_question_pack`

```sql
CREATE TABLE IF NOT EXISTS student_tower_question_pack (
    pack_id VARCHAR(64) PRIMARY KEY,
    run_id VARCHAR(64) NOT NULL,
    node_id VARCHAR(64) NOT NULL,
    student_no VARCHAR(64) NOT NULL,
    course_code VARCHAR(64) NOT NULL,
    mode VARCHAR(32) NOT NULL,
    question_ids_json TEXT NOT NULL,
    source VARCHAR(32) DEFAULT 'rule',
    strategy_json TEXT,
    ai_reason TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_tower_question_pack_node
ON student_tower_question_pack(run_id, node_id, mode);
```

字段说明：

- `mode`: `diagnosis/battle/boss/elite`
- `question_ids_json`: 保留题目顺序。
- `source`: `ai/rule/mixed/fallback`
- `strategy_json`: 记录难度、题型比例、候选数量、过滤条件。
- `ai_reason`: AI 选择或重排说明。

### 4.3 题目使用历史复用 attempt

不急着新建 usage 表，第一版直接从：

- `student_tower_attempt.answer_summary_json`
- `submission_answer`
- `task_submission`

统计最近做过和最近错过的题。

如果后续需要更快查询，再新增：

```sql
CREATE TABLE student_question_usage (
    id VARCHAR(64) PRIMARY KEY,
    student_no VARCHAR(64) NOT NULL,
    course_code VARCHAR(64) NOT NULL,
    question_id VARCHAR(64) NOT NULL,
    knowledge_point_id VARCHAR(64),
    ability_point_id VARCHAR(64),
    correct BOOLEAN,
    source VARCHAR(32),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 4.4 能力雷达数据不必新增表

优先复用：

- `student_ability_delta_log.before_score`
- `student_ability_delta_log.after_score`
- `CompetencyScore`
- `CompetencyScoreHistory`
- `knowledge_mastery`

规则：

- 查某个 `node_id` 时，以该节点写入的 delta 为本次变化依据。
- 没有 delta 的能力点，`beforeScore = afterScore = 当前能力分`。
- 查整个 `run_id` 时，以 run 中每个能力点第一条 delta 的 `beforeScore` 作为通关前，最后一条 delta 的 `afterScore` 作为通关后。
- 如果没有历史 delta，则用当前能力分和知识点掌握度聚合兜底。

## 5. 后端实施任务

### Task 1：实现路线模板库

新增：

- `TowerRouteTemplateCatalog.java`
- `TowerRouteTemplate.java`
- `TowerTemplateNode.java`

修改：

- `TowerRunServiceImpl#planNodes`
- `TowerRunServiceImpl#fallbackNodes`
- `TowerRunServiceImpl#aiPlannedNodes`

实现方式：

1. 后端内置 4 到 6 套模板。
2. AI 返回 `templateId` 和重点知识点列表。
3. 后端用模板节点生成真实节点。
4. 如果 AI 超时或返回非法模板，使用规则选择模板。
5. `student_tower_run.ai_snapshot_json` 记录 AI 建议和最终采用模板。

验收：

- 首次生成不依赖 AI 也能在较短时间返回。
- 不同学生仍会因为模板、知识点、难度、辅助房位置不同而看到不同路线。
- 地图不再表现为“正在让 AI 现场画节点”。

### Task 2：路线生成性能优化

修改：

- `TowerRunServiceImpl#getOrCreateActiveRun`
- `TowerRunServiceImpl#supportIndexes`
- `ProfileApiController#getTowerRun`

优化点：

- active run 已存在时绝不调用 AI。
- `supportIndexes(courseCode)` 在一次请求内只构建一次，避免每个节点重复查知识点和能力点。
- AI 调用设置短超时，超时立即规则兜底。
- 可选：登录或选择课程后预生成 run。

验收：

- 第二次进入地图只读数据库，不重新规划。
- 首次进入即使 AI 不可用也能快速显示规则模板路线。

### Task 3：实现题包推荐服务

新增：

- `StudentTowerQuestionPack.java`
- `StudentTowerQuestionPackMapper.java`
- `TowerQuestionPackService.java`
- `TowerQuestionPackServiceImpl.java`

核心方法：

```java
Map<String, Object> getOrCreateQuestionPack(
    String studentNo,
    String runId,
    String nodeId,
    String mode
);
```

候选题来源：

- `QuestionService.filterQuestions(courseCode, null, knowledgePointId, type, difficulty, null)`
- 同课程同知识点题。
- Boss 节点可扩大到本 run 已涉及知识点。
- 如果当前知识点题不足，可扩展到关联能力点下的其他知识点。

规则打分：

```text
score =
  knowledgeMatch * 40
  + difficultyFit * 20
  + weakKnowledgeBoost * 15
  + wrongHistoryBoost * 15
  + typeDiversityBoost * 5
  - recentUsedPenalty * 30
```

题量建议：

- diagnosis：3 题，优先单选/填空，难度围绕当前掌握度。
- battle：5 题，题型混合，难度随节点 difficulty 增加。
- elite：6 题，加入多选/编程/简答。
- boss：8 题，覆盖本 run 多个知识点。

验收：

- 同一知识点不会永远取前几道题。
- 最近做过的题会被降权。
- 最近错过的知识点会被加强。
- 数据库有足够题时不使用组件 fallback。

### Task 6：新增能力雷达服务和 API

新增：

- `AbilityRadarService.java`

API：


计算规则：

## 7. AI 能力边界

### 应该交给 AI 的事

- 判断学生适合哪套路线模板。
- 从候选题 ID 中选择最合适的题。
- 给出诊断解释、能力变化解释。
- 给出下一步学习建议。

### 不应该交给 AI 的事

- 页面加载时临时生成完整节点 UI。
- 直接生成数据库不存在的题目。
- 决定最终通关状态。
- 绕过后端校验修改分数。
- 返回未经校验的知识点和能力点。

## 8. 推荐实施顺序

1. 先做题包 API，让战斗房/诊断房真正使用数据库题库。
2. 再做诊断全对自动奖励结算，解决流程延迟。
3. 接着做能力雷达接口和前端 ECharts 展示。
4. 然后把路线生成改成模板库 + AI 选择，降低首次加载延迟。
5. 最后接入 AI 题目重排和 AI 雷达总结。

## 9. 最小可展示版本范围

如果时间有限，优先实现：

1. `student_tower_question_pack` 表。
2. `TowerQuestionPackService` 规则推荐题。
3. `DiagnosisRoom/BattleRoom` 改用题包。
4. 诊断全对自动进入奖励。
5. `ability-radar` 接口。
6. `StudentAbilityMapPanel.vue` 雷达图。
7. 路线模板库规则选择。

AI 题目重排和 AI 模板选择可以第二步接入；第一步先把“快、真、可用”的闭环打稳。

## 10. 验收清单

- 首次进入地图时，即使 AI 不可用也能快速看到完整路线。
- 刷新地图不会重新生成路线。
- 节点数量、房间类型和布局来自后端模板/选择结果，不是前端固定写死。
- 战斗房题目来自数据库题库。
- 诊断房题目来自数据库题库。
- 同一知识点多次进入不会总是相同前三道题。
- 诊断全对后自动进入奖励，不需要手动跳转。
- 通关后结算页能看到能力雷达前后对比。
- 回到能力图谱页也能看到本次能力变化。
- AI 慢、失败或返回非法数据时，规则兜底可以保证流程继续。
