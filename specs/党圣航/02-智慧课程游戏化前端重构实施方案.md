# 智慧课程游戏化前端重构实施方案

## 1. 目标与现状判断

当前前端已经具备爬塔课程的雏形：`TowerMap.vue` 承载地图，`FloorView.vue` 承载楼层流程，`GameHud.vue` 展示 HP、ATK、DEF、EXP、COIN、ENERGY，`BattleRoom.vue`、`DiagnosisRoom.vue`、`GameRoomModal.vue` 分别承载战斗、诊断和非战斗房间。

主要问题不在于是否有暗色皮肤，而在于交互结构仍偏“课程网站”：诊断房、战斗房、结算像功能标签或阶段侧栏，玩家是在切换页面模块，而不是在地图上选择节点、进入事件、完成挑战、获得奖励、返回地图继续规划。

本次重构目标是将现有系统从“课程页面 + 游戏化皮肤”重构为“课程 Run + 节点事件 + 战斗回合 + 奖励构筑”的游戏化学习流程，形成类似《杀戮尖塔》的连续状态变化和选择后果。

## 2. 重构范围

### 2.1 需要重点重构的前端文件

- `frontend/src/views/TowerMap.vue`
  - 从单线课程目录改为分支路线地图。
  - 地图节点成为所有学习事件的入口。
  - 删除“下一步自动进入”的主导感，强化玩家选择路线。

- `frontend/src/views/FloorView.vue`
  - 从“诊断房 / 战斗房 / 结算”的页面阶段侧栏，改为节点事件状态机。
  - 楼层内不再表现为标签页流程，而是表现为“进入房间后发生的连续事件”。

- `frontend/src/components/GameHud.vue`
  - 保留核心状态，但压缩为游戏 HUD。
  - 加入图标化资源展示，减少后台数据看板感。

- `frontend/src/components/BattleRoom.vue`
  - 从题目表单改为战斗场景。
  - 玩家、敌人、敌人意图、知识卡牌、能量、题目反馈要在同一个战斗舞台中形成闭环。

- `frontend/src/components/DiagnosisRoom.vue`
  - 从普通诊断题列表改为开局侦察事件或楼层侦察事件。
  - 诊断结果必须影响本局状态，而不是只决定是否跳过战斗。

- `frontend/src/components/GameRoomModal.vue`
  - 非战斗房间不再使用统一网站弹窗承载全部内容。
  - 拆成休息点、宝箱、商店、随机事件等独立场景组件。

## 3. 总体流程设计

重构后的主流程按“一局课程 Run”组织：

```text
选择课程 / 进入课程副本
↓
开局诊断：生成本局初始状态、弱点、初始卡组
↓
进入概念地图：选择可达路线节点
↓
进入节点事件：战斗 / 精英 / Boss / 宝箱 / 休息 / 商店 / 随机事件
↓
完成节点挑战：答题、调试、编程、复习、选择资源
↓
结算节点结果：HP、金币、经验、掌握度、错题、卡牌变化
↓
奖励选择：三选一或跳过
↓
返回地图：路线解锁、状态刷新、继续选择
↓
章节 Boss：综合项目挑战
↓
本局结算：路线回放、掌握变化、弱点、奖励、下一局建议
```

流程重点：学生的每次操作都要造成可见状态变化，并影响下一步路线选择。

## 4. 第一阶段：课程 Run 入口

### 4.1 页面职责

学生进入课程后，不直接进入课程详情页或题目页，而是进入课程副本入口。

入口页面可以继续使用 `/tower-map`，但首次进入时显示“开始本局”的覆盖层或起始节点。

### 4.2 实现方案

1. 在 `runStore.js` 中维护本局状态：

```js
{
  runId,
  courseId,
  courseName,
  studentId,
  phase: 'intro' | 'diagnosis' | 'map' | 'node' | 'combat' | 'reward' | 'settlement',
  profile: { hp, maxHp, atk, def, exp, coins, energy, level },
  deck: [],
  relics: [],
  weakConcepts: [],
  routeNodes: [],
  currentNodeId,
  lastNodeResult
}
```

2. `TowerMap.vue` 初始化时：
   - 调用 `getStudentProfile(studentId, courseId)` 获取状态。
   - 调用 `getTowerMap(studentId, courseId)` 获取节点。
   - 如果后端暂未提供 runId，则前端用 `studentId + courseId + 日期` 生成临时 runKey。

3. 若学生没有完成开局诊断：
   - `phase` 设为 `diagnosis`。
   - 地图节点锁定，只显示入口节点“诊断房”。

### 4.3 UI 设计

- 背景：使用新生成的“课程高塔入口”背景图。
- 中央：课程名、章节 Act、开始 Run 按钮。
- 左下：小人角色，显示 HP 与等级。
- 右侧：本局规则摘要，如“本局目标：击败 Python 基础语法 Boss”。

### 4.4 资产要求

- 新生成：
  - `backgrounds/bg-run-entry-python-tower.png`
  - 画面：暗色知识高塔入口、发光路径、远处塔顶、前景留出按钮区域。
- 现有图标：
  - 小人图标：作为玩家头像。
  - HP 血条：作为入口状态条。
- 可继续使用 Element Plus 图标：
  - `ArrowRight` 或 `CaretRight`：开始按钮辅助图标。

## 5. 第二阶段：开局诊断事件

### 5.1 设计意图

诊断不是一个固定标签页，而是本局开局事件，类似《杀戮尖塔》的开局祝福。它决定本局初始条件，让学生感受到“测评结果影响冒险”。

### 5.2 操作流程

```text
进入诊断房
↓
系统抽取 3-5 道覆盖当前章节核心概念的题
↓
学生答题
↓
系统生成诊断结果
↓
学生获得初始奖励或负面状态
↓
进入地图
```

### 5.3 实现方案

1. 保留 `DiagnosisRoom.vue` 的题目加载逻辑：
   - `getTaskQuestions(taskNo)`
   - `getQuestionById(questionId)`
   - `getQuestionsByKnowledgePoint(courseId, kpId)`

2. 改造结果输出：

```js
emit('diagnosed', {
  status: 'mastered' | 'partial' | 'weak',
  correctRate,
  weakConcepts: [
    { kpId, kpName, reason: 'single_choice_error' }
  ],
  initialRewards: [
    { type: 'card', cardId: 'trace_variable' },
    { type: 'coin', amount: 20 }
  ],
  initialCurses: [
    { type: 'concept_debuff', concept: '变量作用域' }
  ]
})
```

3. `FloorView.vue` 或新的 `RunShell.vue` 接收结果后：
   - 更新 `runStore.weakConcepts`。
   - 弱点概念在地图上标记为高风险节点。
   - 生成初始卡组，如“变量追踪”“缩进护盾”“运行一下”。

4. 调用现有 `sendGameEvent(studentId, body)`：

```js
sendGameEvent(studentId, {
  course_id: courseId,
  event_type: 'diagnosis_finished',
  correct_rate: correctRate,
  weak_concepts: weakConcepts
})
```

### 5.4 UI 设计

- 背景：新生成“诊断室/代码侦察室”。
- 题目不再用普通卡片堆叠，要表现为“侦察卷轴”或“分析面板”。
- 完成后显示三块结果：
  - 掌握概念：绿色或蓝色光效。
  - 薄弱概念：红色警示。
  - 初始奖励：卡牌或资源。

### 5.5 资产要求

- 新生成：
  - `backgrounds/bg-diagnosis-lab.png`
  - `cards/card-trace-variable.png`
  - `cards/card-indent-shield.png`
  - `cards/card-run-code.png`
- 现有图标：
  - 小人图标：学生角色。
  - HP 血条：展示诊断前后状态。
- Element Plus 图标：
  - `Search`：诊断/侦察。
  - `Warning`：薄弱点提示。
  - `CircleCheck`：掌握点。

## 6. 第三阶段：概念地图重构

### 6.1 设计意图

地图是游戏感的核心。当前地图更像线性课程进度，需要改为分支路线。学生必须在不同节点间做选择，并承担结果。

### 6.2 地图节点类型

| 节点类型 | 游戏含义 | 学习含义 | 图标来源 |
|---|---|---|---|
| battle | 普通战斗 | 常规概念题 / 基础练习 | 现有骷髅头图标 |
| elite | 精英战斗 | 多知识点综合练习 | 现有骷髅头图标强化版或新生成精英骷髅 |
| boss | Boss 战 | 章节综合项目 / 大题 | 新生成 Boss 头标 |
| event | 随机事件 | 代码陷阱 / 学习情境选择 | Element Plus `QuestionFilled` 或新生成问号牌 |
| treasure | 宝箱 | 课程资源 / 卡牌奖励 | Element Plus `Box` 可先用，后续生成宝箱图标 |
| rest | 休息点 | 复习、回血、升级卡牌 | 新生成篝火/书桌图标 |
| shop | 商店 | 用金币换提示、删错题卡、强化 | Element Plus `ShoppingCart` 或新生成书商图标 |

### 6.3 实现方案

1. 新增 `TowerRouteMap.vue`：
   - 接收 `nodes` 和 `edges`。
   - 支持节点悬停、点击、禁用状态、已通关状态。
   - 地图不再强制一列排列，按层级渲染为 2-4 个分支。

2. 后端若暂时只返回线性楼层，前端先生成伪分支：

```js
function buildRouteRows(floors) {
  return floors.map((floor, index) => ({
    level: index + 1,
    nodes: makeBranchNodes(floor, index),
    edges: makeEdges(index)
  }))
}
```

3. `RouteNode.vue` 节点状态：

```js
{
  nodeId,
  kpId,
  kpName,
  roomType,
  level,
  status: 'locked' | 'available' | 'cleared' | 'weak' | 'selected',
  risk: 'low' | 'normal' | 'high',
  rewardPreview: ['coin', 'card', 'resource'],
  prerequisites: []
}
```

4. 节点点击逻辑：
   - locked：显示锁定原因。
   - available/weak：先打开 `NodePreviewPanel`，再由玩家确认进入。
   - 不再使用“进入可选房间”按钮作为主入口。

5. 右侧信息面板 `NodePreviewPanel.vue`：
   - 显示房间类型、知识点、风险、奖励、推荐理由。
   - 只展示当前悬停或选中的节点，不做常驻数据看板。

### 6.4 UI 设计

- 地图背景使用“知识高塔内部 / 山路 / 星图路线”。
- 节点用图标而不是文字卡片作为第一视觉。
- 鼠标悬停节点时：
  - 节点发光。
  - 连接线高亮。
  - 右侧显示预览。
- 已通关节点显示熄灭或盖章。
- 薄弱节点显示红色裂纹或警示边框。

### 6.5 资产要求

- 新生成：
  - `backgrounds/bg-route-map-act1.png`
  - `backgrounds/bg-route-map-act2.png`
  - `backgrounds/bg-route-map-act3.png`
  - `icons/icon-boss.png`
  - `icons/icon-rest-site.png`
  - `icons/icon-elite-skull.png`
- 现有图标：
  - `icons/icon-skull.png`：普通战斗。
  - `icons/icon-hp-bar.png`：地图右侧状态摘要。
  - `icons/icon-player.png`：当前玩家所在位置。
- Element Plus 过渡使用：
  - `Box`：宝箱。
  - `ShoppingCart`：商店。
  - `QuestionFilled`：事件。

## 7. 第四阶段：节点进入与房间状态机

### 7.1 设计意图

删除左侧“诊断房 / 战斗房 / 结算”的标签式流程，改为由节点类型决定房间事件。

### 7.2 状态机设计

`RunShell.vue` 维护当前阶段：

```js
const phase = ref('map')

const transitions = {
  map: ['nodePreview'],
  nodePreview: ['combat', 'rest', 'treasure', 'shop', 'event', 'map'],
  combat: ['reward', 'settlement', 'map'],
  rest: ['map'],
  treasure: ['map'],
  shop: ['map'],
  event: ['combat', 'reward', 'map'],
  reward: ['map'],
  settlement: ['map']
}
```

### 7.3 实现方案

1. `TowerMap.vue` 只负责 Run 外壳和地图。
2. 点击节点后设置：

```js
runStore.currentNodeId = node.nodeId
runStore.phase = node.roomType === 'battle' ? 'combat' : node.roomType
```

3. 根据 `phase` 渲染组件：

```vue
<TowerRouteMap v-if="phase === 'map'" />
<CombatStage v-else-if="phase === 'combat'" />
<RestSiteRoom v-else-if="phase === 'rest'" />
<TreasureRoom v-else-if="phase === 'treasure'" />
<ShopRoom v-else-if="phase === 'shop'" />
<EventRoom v-else-if="phase === 'event'" />
<RewardDraft v-else-if="phase === 'reward'" />
<SettlementReport v-else-if="phase === 'settlement'" />
```

4. 完成节点后必须回到地图：
   - 地图中当前节点状态改为 `cleared` 或 `weak`。
   - 解锁下一层可达节点。
   - HUD 刷新。

## 8. 第五阶段：战斗房重构

### 8.1 设计意图

战斗房不能只是答题表单。题目要被包装成“回合制知识战斗”：学生看敌人意图，选择知识卡牌，消耗能量，回答题目，造成伤害或受到伤害。

### 8.2 战斗界面布局

```text
┌────────────────────────────────────────────┐
│ 顶部 HUD：HP / 护盾 / 金币 / 能量 / 回合数 │
├────────────────────────────────────────────┤
│ 左：玩家小人 + HP/护盾      右：知识敌人 + 意图 │
│                                            │
│ 中央：当前题目/代码片段/反馈动画             │
│                                            │
│ 底部：知识卡牌手牌 + 结束回合按钮            │
└────────────────────────────────────────────┘
```

### 8.3 战斗数据结构

```js
{
  turn: 1,
  player: {
    hp,
    block,
    energy,
    maxEnergy,
    hand: [],
    drawPile: [],
    discardPile: []
  },
  enemy: {
    id,
    name,
    hp,
    maxHp,
    intent: 'attack' | 'defend' | 'debuff' | 'quiz' | 'code',
    intentValue,
    conceptId
  },
  activeQuestion,
  battleLog: []
}
```

### 8.4 卡牌设计

第一版不需要完整卡牌游戏，可以把现有操作卡牌化：

| 卡牌 | 类型 | 能量 | 效果 | 来源 |
|---|---|---:|---|---|
| 直接作答 | 攻击 | 1 | 提交当前题，答对造成伤害 | 默认卡 |
| 查看提示 | 技能 | 1 | 调用 `sendGameEvent` 记录提示，降低奖励 | 默认卡 |
| 运行一下 | 技能 | 1 | 对编程题显示运行提示或示例 | 新奖励卡 |
| 缩进护盾 | 防御 | 1 | 本回合答错少扣 HP | 诊断奖励 |
| 变量追踪 | 技能 | 1 | 变量题排除一个干扰项 | 诊断奖励 |
| 跳过 | 技能 | 2 | 跳过当前题但不造成伤害 | 现有跳过操作卡牌化 |

### 8.5 战斗规则

1. 进入战斗时抽 3 张或 5 张卡。
2. 每回合恢复固定能量，例如 3 点。
3. 学生使用卡牌后触发答题、提示、防御、跳过等动作。
4. 答对：
   - 敌人扣血。
   - 根据 ATK 或题目难度计算伤害。
5. 答错：
   - 敌人按意图造成伤害。
   - 当前知识点加入弱点或错题记录。
6. 敌人 HP 为 0：进入奖励选择。
7. 玩家 HP 为 0：进入失败结算或提示返回休息点。

### 8.6 与现有接口对接

- 题目加载继续使用：
  - `getTaskQuestions(taskNo)`
  - `getQuestionById(questionId)`
  - `getQuestionsByKnowledgePoint(courseId, kpId)`
- 提交继续使用：
  - `submitTask(formData)`
- 游戏事件继续使用：
  - `sendGameEvent(studentId, body)`

事件类型建议：

```js
answer_correct
answer_wrong
card_played
hint_used
answer_skipped
battle_started
battle_finished
reward_picked
node_cleared
```

## 9. 第六阶段：奖励选择重构

### 9.1 设计意图

每次战斗后必须出现选择，而不是只显示结算。奖励选择是游戏构筑感的来源。

### 9.2 操作流程

```text
战斗胜利
↓
展示金币、经验、掌握度变化
↓
出现 3 张奖励卡
↓
学生选择 1 张或跳过换金币
↓
奖励进入本局卡组/遗物/资源
↓
返回地图
```

### 9.3 奖励类型

| 类型 | 示例 | 作用 |
|---|---|---|
| card | 变量追踪、缩进护盾、循环连击 | 加入本局卡组 |
| relic | 专注徽章、调试护符 | 本局被动加成 |
| coin | 金币 | 商店消费 |
| heal | 恢复 HP | 提升续航 |
| resource | 课程资料、代码模板 | 跳转课程资源或加入背包 |

### 9.4 实现方案

1. 新增 `RewardDraft.vue`。
2. 根据节点类型和战斗结果生成奖励：

```js
function buildRewardOptions(node, result) {
  if (node.roomType === 'elite') return [rareCard, relic, coinBundle]
  if (result.correctRate >= 0.9) return [upgradedCard, card, coinBundle]
  return [card, heal, resource]
}
```

3. 选择奖励后：
   - 更新 `runStore.deck` 或 `runStore.relics`。
   - 调用 `sendGameEvent` 记录 `reward_picked`。
   - 返回地图。

### 9.5 UI 资产要求

- 新生成：
  - `backgrounds/bg-reward-chamber.png`
  - `cards/card-reward-frame-common.png`

## 16. 验收标准

### 16.1 流程验收

- 学生进入课程后，默认体验是“开始/继续一局 Run”，而不是进入普通课程网站页面。
- 诊断、战斗、休息、宝箱、商店、结算都从地图节点进入。
- 页面上不再出现“诊断房 / 战斗房 / 结算”作为类似标签页的主导航。
- 完成任意节点后必须返回地图，并能看到节点状态变化。
- 至少存在一处路线分支，学生可以在两个及以上可达节点中做选择。
- 战斗胜利后必须出现奖励选择，且选择会影响后续状态。

### 16.2 游戏感验收

- 地图第一视觉是路线和节点，不是右侧说明栏或顶部数据表。
- 战斗第一视觉是玩家、敌人、敌人意图、手牌，不是普通题目表单。
- HP、金币、能量至少有图标和状态变化反馈。
- 普通战斗、精英战斗、Boss 在图标、背景或敌人形象上能明显区分。
- 鼠标悬停地图节点有高亮反馈，点击节点有确认进入反馈。
- 答对、答错、使用提示、跳过题目都有可见反馈。

### 16.3 学习功能验收

- 诊断结果能生成薄弱概念，并在地图或战斗中体现。
- 战斗题目仍能正常加载、作答、提交。
- 提示和跳过仍能调用 `sendGameEvent` 记录。
- 商店能读取错题，并将错题表现为可处理的学习对象。
- 宝箱能读取课程资源或生成卡牌奖励。
- 结算页能展示本局学习表现，而不是只显示单一分数。

### 16.4 视觉资产验收

- `frontend/src/assets/game/` 下按背景、角色、敌人、图标、卡牌分类存放。
- 使用现有骷髅头、HP 血条、小人图标的地方必须在资产清单中标注。
- 新生成背景图不得包含不可控文字或 Logo。
- 背景图要为 UI 留出安全区域，不能遮挡题目、按钮和卡牌。
- 在 1920x1080 和 1366x768 下，主要 UI 不重叠、不溢出。
- 移动端或窄屏下，地图与战斗至少能纵向浏览，不出现按钮文字挤出容器。

### 16.5 技术验收

- `npm run build` 通过。
- 控制台无关键运行时错误。
- 新增组件 props 和 emits 有清晰命名。
- 旧接口失败时仍有 fallback，不出现空白页。
- 不引入新的大型依赖；第一版使用 Vue 3、Pinia、Element Plus、CSS 动画即可。

## 18. 风险与处理策略

- 后端暂时不支持分支地图：
  - 前端用现有 `getTowerMap` 数据生成伪分支，后端字段补齐后替换。

- 新生成图片风格不统一：
  - 固定 prompt 风格关键词，统一尺寸和色调；背景不要带文字。

- 游戏机制过重影响学习效率：
  - 第一版卡牌只包装现有操作，不做复杂牌库、抽牌堆和遗物系统。

- 学生不知道下一步该做什么：
  - 地图保留高亮可达节点和右侧节点预览，但不要恢复成网站标签页。

- 题目提交逻辑被重构破坏：
  - `BattleRoom.vue` 的加载、判分、提交函数先迁移复用，UI 逐步替换。

## 19. 最终判断标准

重构完成后，用户不应再感觉这是一个“分了几个标签页的课程网站”。学生进入后应自然理解为：

“我正在进行一局 Python 课程爬塔。我需要选择路线，进入节点，打败知识敌人，拿到奖励，强化自己的学习卡组，最后挑战章节 Boss。”

只有当地图选择、战斗反馈、奖励选择和状态变化形成连续闭环时，才算完成本次游戏化重构。
## 20. 设计校正：从“面板化卡牌战斗”调整为“场景对话式答题”

### 20.1 判定结论

本方案前 1、3、7、16、19 节关于“不能只是课程网站加游戏皮肤”的方向是正确的，但第 8 节战斗界面仍然偏向《杀戮尖塔》的卡牌手牌布局，容易在实现时继续形成“中间题目卡片 + 左右数据栏 + 顶部标签”的网站式构图。

本轮实现反馈证明，单纯把生成背景图放到页面后面，再叠加传统卡片、侧栏、表单，并不能形成游戏感。因此后续实现需要把背景图视为主舞台，而不是页面装饰。

### 20.2 新的界面硬性要求

- 地图页必须以生成的地图/卷轴背景作为主视觉，路线节点直接落在背景中的地图区域上，不再使用大面积暗色容器包住地图。
- 节点预览只能作为轻量浮层出现，不再常驻多个后台面板，如“Run Status”“Room Types”等。
- 诊断房和战斗房采用类似开放世界 RPG 对话的构图：场景背景、角色站位、底部对话文本、右侧答案选项。
- 题目不再表现为表单卡片或题目列表，而是表现为角色/系统提出的问题。
- 学生通过选择对话答案推进流程；单选题点击选项即判定，多选题选择后确认，填空/编程题输入后确认。
- 答对：敌人扣血，学生不扣血。
- 答错：根据敌人意图扣学生 HP，并显示受击反馈。
- 跳过：不造成伤害，也不扣 HP，但不计正确。
- 诊断题不扣 HP，但会形成侦察结果，影响后续战斗风险和奖励判断。

### 20.3 当前实现落点

- `BattleRoom.vue` 改为场景对话式战斗，保留题目加载、提交、`sendGameEvent` 等原接口。
- `DiagnosisRoom.vue` 改为场景对话式侦察，保留诊断结果输出。
- `FloorView.vue` 在诊断、战斗、Boss 阶段进入场景模式，隐藏右侧情报栏和流程标签。
- `TowerMap.vue` 去掉地图大卡片容器，路线节点覆盖在生成地图背景上，仅保留当前节点浮层预览。

### 20.4 新验收补充

- 1920x1080 或 1440x900 下，战斗页第一视觉必须是“背景场景 + 角色 + 对话答案”，不能是题目表单。
- 诊断页第一视觉必须是“侦察场景 + 对话答案”，不能是三张题目卡片。
- 地图页第一视觉必须是地图背景和节点，不能是大卡片里的路线图。
- 点击错误答案后，学生 HP 必须下降并出现可见反馈；点击正确答案后，学生 HP 不下降。
- 无后端题库时必须使用本地演示题卡，保证课堂展示流程不断档。
