# 个性化爬塔路线与通关解锁实施计划

## 1. 目标

把当前“前端固定路线 + 本地房间分支”的爬塔流程改成真正可持久化、可解锁、可个性化生成的学习 Run。

最终效果：

1. 玩家只能进入已解锁节点；通过当前战斗节点后，下一关战斗节点才会解锁。
2. 商店、补给房、休息点、宝箱、随机事件等辅助房间不再固定出现在首页，而是由后端路线数据决定，并且可以绑定到某个战斗节点，随该战斗节点通关后解锁。
3. 每个学生在每门课都有自己的爬塔路线和当前进度，后端真实记录“走到了哪一个关卡、哪些节点已通关、哪些节点可进入”。
4. 路线数量和布局不固定，由 AI 根据学生历史闯关、掌握度、错题、能力画像和课程知识图谱生成个性化节点序列。
5. 诊断房全对时，等价于直接通过对应战斗房；后端记录通关，地图显示已通关，并解锁后续节点。
6. 通关后的能力图谱要真实反映能力变化，不能只是静态平均值。
7. 诊断要结合 AI 给出具体诊断报告，包括薄弱原因、建议、推荐题型、是否允许跳过战斗。

## 2. 当前问题判断

### 2.1 前端路线仍然固定

`frontend/src/views/TowerMap.vue` 当前存在固定逻辑：

- `roomPattern` 写死房间顺序。
- `fallbackNames` 写死演示楼层名称。
- `branchRoomTypes(node, index)` 按 index 固定生成诊断、战斗、宝箱、休息、商店分支。
- `branchStatus(node, index, branch)` 在前端推断分支是否可进入。

这导致首页节点看起来像个路线图，但事实源不在后端；后端只返回知识点楼层，前端再自行“装配”房间。

### 2.2 后端只有知识点状态，没有路线节点实例

已有表和服务：

- `knowledge_point_floor_status`：能记录某个学生某课程某知识点的 `cleared/weak` 状态。
- `FloorProgressServiceImpl`：监听 `floor_cleared/floor_failed`，写入知识点状态。
- `ProfileServiceImpl#getTowerMap`：按课程知识点顺序生成地图。

缺口：

- 没有 `run_id`。
- 没有 `node_id`。
- 没有“第几关、什么房间、属于哪条路线、父节点是谁、通关后解锁谁”的结构。
- 辅助房间无法与战斗关卡绑定。
- 学生当前进度只能从知识点状态推断，不能精确表示“正在第几个节点”。

### 2.3 诊断房没有 AI 诊断闭环

`frontend/src/components/DiagnosisRoom.vue` 当前只做本地判分：

- 计算 `correctRate`。
- `correctRate >= 0.85` 返回 `mastered`。
- `FloorView.vue` 里如果 `mastered` 就前端发送 `floor_cleared`。

缺口：

- 没有把题目、答案、知识点、能力点上下文交给 AI 生成诊断。
- 没有后端诊断报告。
- 没有“全对才直接通关”的硬规则；当前是 `>= 0.85`，三题场景下 2/3 也可能接近但不应等同全对。
- 通关跳过战斗后，后端没有记录“通关方式是 diagnosis_perfect”。

### 2.4 能力图谱变化不够真实

`frontend/src/components/StudentAbilityMapPanel.vue` 当前根据：

- `getAbilityMap(courseCode)`
- `getKnowledgeGraph(courseCode)`
- `getKnowledgeMastery(studentNo, courseCode)`

做前端聚合和平均。

缺口：

- 战斗通关、诊断全对、失败、错题没有稳定映射到能力点变化解释。
- 前端看不到“本次通关使哪些能力提升、为什么提升、下一步建议是什么”。
- AI 没有参与能力变化说明。

## 3. 目标架构

### 3.1 后端成为路线事实源

前端不再根据 index 生成房间。前端只做展示：

```text
GET /api/students/{studentId}/tower-map?course_id=...
        ↓
后端返回完整路线节点
        ↓
TowerMap.vue 只渲染 node.row / node.col / node.status / node.roomType
```

后端负责：

- 路线生成。
- 路线持久化。
- 进度推进。
- 解锁判断。
- 辅助房间绑定。
- AI 个性化生成。
- AI 诊断报告。
- 能力变化写入。

### 3.2 一门课一个当前 Run

每个学生每门课维护一个当前 Run：

```text
student + course
  └── tower_run
        ├── node 1: diagnosis / available
        ├── node 2: battle / locked
        ├── node 3: shop / locked, unlockAfter=node2
        ├── node 4: rest / locked, unlockAfter=node2
        ├── node 5: battle / locked, unlockAfter=node2
        └── ...
```

当学生进入地图：

1. 如果没有 active run，后端自动生成一个。
2. 如果已有 active run，直接返回已有路线和进度。
3. 如果教师或学生显式要求重新生成，才创建新版本路线；旧 run 标记为 `archived`。

### 3.3 AI 只负责生成建议，后端负责校验落库

AI 可以决定：

- 总节点数量。
- 战斗房数量。
- 诊断房数量。
- 休息点数量。
- 商店/补给/宝箱出现位置。
- 哪些知识点应该优先练。
- 哪些节点更难。

但后端必须校验：

- 至少 1 个战斗节点。
- 至少 1 个终点节点，可以是 `boss` 或最后一个 `battle`。
- 所有 `knowledgePointId` 必须属于当前课程。
- 所有 `abilityPointId` 必须属于当前课程。
- 所有非首节点必须有可达前置节点。
- 辅助房间必须绑定到一个已存在的战斗节点或前置节点。
- AI 返回不可用时，用规则生成兜底路线。

## 4. 数据模型

### 4.1 新增表：`student_tower_run`

记录学生某课程的一次个性化爬塔路线。

```sql
CREATE TABLE IF NOT EXISTS student_tower_run (
    run_id VARCHAR(64) PRIMARY KEY,
    student_no VARCHAR(64) NOT NULL,
    course_code VARCHAR(64) NOT NULL,
    version INTEGER DEFAULT 1,
    status VARCHAR(32) DEFAULT 'active',
    route_source VARCHAR(32) DEFAULT 'ai',
    current_node_id VARCHAR(64),
    ai_snapshot_json TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_tower_run_student_course
ON student_tower_run(student_no, course_code, status);
```

字段说明：

- `status`: `active/completed/archived`
- `route_source`: `ai/rule/fallback`
- `current_node_id`: 当前推荐进入的节点，不等于唯一可进入节点。
- `ai_snapshot_json`: 生成路线时输入摘要和 AI 输出，便于排查。

### 4.2 新增表：`student_tower_node`

记录 Run 中每一个具体节点。

```sql
CREATE TABLE IF NOT EXISTS student_tower_node (
    node_id VARCHAR(64) PRIMARY KEY,
    run_id VARCHAR(64) NOT NULL,
    node_order INTEGER NOT NULL,
    row_no INTEGER NOT NULL,
    col_no INTEGER NOT NULL,
    room_type VARCHAR(32) NOT NULL,
    status VARCHAR(32) DEFAULT 'locked',
    knowledge_point_id VARCHAR(64),
    ability_point_id VARCHAR(64),
    parent_node_id VARCHAR(64),
    unlock_after_node_id VARCHAR(64),
    difficulty INTEGER DEFAULT 1,
    ai_reason TEXT,
    payload_json TEXT,
    cleared_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_tower_node_run_order
ON student_tower_node(run_id, node_order);

CREATE INDEX IF NOT EXISTS idx_tower_node_unlock
ON student_tower_node(run_id, unlock_after_node_id);
```

字段说明：

- `room_type`: `diagnosis/battle/elite/boss/rest/shop/treasure/supply/event`
- `status`: `locked/available/cleared/failed/disabled`
- `parent_node_id`: 表示辅助房间属于哪个主战斗节点。
- `unlock_after_node_id`: 该节点在哪个节点通关后解锁。
- `payload_json`: 存放房间配置，例如商店商品池、休息点恢复量、宝箱资源、诊断题数。

### 4.3 新增表：`student_tower_attempt`

记录每次进入房间的尝试结果。

```sql
CREATE TABLE IF NOT EXISTS student_tower_attempt (
    attempt_id VARCHAR(64) PRIMARY KEY,
    run_id VARCHAR(64) NOT NULL,
    node_id VARCHAR(64) NOT NULL,
    student_no VARCHAR(64) NOT NULL,
    course_code VARCHAR(64) NOT NULL,
    room_type VARCHAR(32) NOT NULL,
    result VARCHAR(32) NOT NULL,
    correct_rate NUMERIC(5, 2),
    hp_left INTEGER,
    answer_summary_json TEXT,
    ai_report_json TEXT,
    started_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    finished_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_tower_attempt_node
ON student_tower_attempt(node_id, finished_at);
```

字段说明：

- `result`: `cleared/failed/diagnosis_perfect/diagnosis_partial/rest_taken/shop_purchased/treasure_opened`
- `answer_summary_json`: 存题目、学生答案、正确性摘要，不存过大原文。
- `ai_report_json`: 诊断报告或战斗复盘。

### 4.4 能力变化复用与补充

已有：

- `CompetencyScore`
- `CompetencyScoreHistory`
- `knowledge_mastery`

建议新增轻量表 `student_ability_delta_log`，用于前端展示“本次变化”。

```sql
CREATE TABLE IF NOT EXISTS student_ability_delta_log (
    id VARCHAR(64) PRIMARY KEY,
    student_no VARCHAR(64) NOT NULL,
    course_code VARCHAR(64) NOT NULL,
    run_id VARCHAR(64),
    node_id VARCHAR(64),
    knowledge_point_id VARCHAR(64),
    ability_point_id VARCHAR(64),
    delta_score INTEGER DEFAULT 0,
    before_score INTEGER,
    after_score INTEGER,
    reason TEXT,
    ai_summary TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_ability_delta_student_course
ON student_ability_delta_log(student_no, course_code, created_at);
```

如果不想加表，也可以先把变化写入 `CompetencyScoreHistory` 的备注字段；但为了“通关后能力图谱体现变化”更清晰，建议加独立日志。

## 5. API 契约

### 5.1 获取当前路线

```http
GET /api/students/{studentId}/tower-run?course_id={courseCode}
```

返回：

```json
{
  "runId": "run-001",
  "studentNo": "1001",
  "courseCode": "1",
  "status": "active",
  "currentNodeId": "node-003",
  "routeSource": "ai",
  "nodes": [
    {
      "nodeId": "node-001",
      "nodeOrder": 1,
      "row": 1,
      "col": 1,
      "roomType": "diagnosis",
      "status": "cleared",
      "knowledgePointId": "kp-001",
      "knowledgePointName": "变量与数据类型",
      "abilityPointId": "ap-001",
      "abilityPointName": "语法基础",
      "difficulty": 1,
      "parentNodeId": "",
      "unlockAfterNodeId": "",
      "aiReason": "该知识点最近答题波动较大，先诊断再决定是否跳过战斗。",
      "clearedAt": "2026-07-01T10:00:00"
    }
  ]
}
```

兼容：

- `GET /api/students/{studentId}/tower-map` 可以继续保留，但内部改为调用 tower-run，并返回 `nodes`。
- 前端 `TowerMap.vue` 的 `normalizeFloors` 改为兼容旧 `floor` 和新 `node` 字段。

### 5.2 生成或重生成路线

```http
POST /api/students/{studentId}/tower-run/generate?course_id={courseCode}&force=false
```

规则：

- `force=false`：有 active run 就返回已有 run。
- `force=true`：归档旧 run，基于当前画像重新生成。

### 5.3 进入节点

```http
POST /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/enter
```

后端校验：

- 节点必须属于当前学生 active run。
- `status` 必须是 `available/failed/cleared`。
- `locked` 不允许进入。
- `cleared` 可以进入复盘模式，但不会重复发放奖励。

### 5.4 完成节点

```http
POST /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/complete
```

请求：

```json
{
  "result": "cleared",
  "correctRate": 0.8,
  "hpLeft": 72,
  "answerSummary": [
    {
      "questionId": "q-001",
      "correct": true,
      "knowledgePointId": "kp-001",
      "abilityPointId": "ap-001"
    }
  ],
  "extra": {
    "roomType": "battle"
  }
}
```

后端行为：

1. 写入 `student_tower_attempt`。
2. 根据结果更新 `student_tower_node.status`。
3. 如果通关，解锁 `unlock_after_node_id = nodeId` 的节点。
4. 如果是战斗节点通关，解锁绑定在该节点上的商店、休息点、宝箱、补给房。
5. 发布已有 `GameEventTypes` 事件，保持画像、掌握度、风险检测链路继续工作。
6. 更新 `knowledge_point_floor_status`。
7. 更新 `knowledge_mastery`。
8. 更新能力分和能力变化日志。
9. 返回更新后的 run 摘要。

### 5.5 AI 诊断

```http
POST /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/diagnose
```

请求：

```json
{
  "answers": [
    {
      "questionId": "q-001",
      "stem": "题干",
      "studentAnswer": "B",
      "correctAnswer": "B",
      "correct": true,
      "knowledgePointId": "kp-001"
    }
  ]
}
```

返回：

```json
{
  "status": "perfect",
  "correctRate": 1.0,
  "battleBypassed": true,
  "diagnosis": {
    "summary": "你对变量命名和基本数据类型掌握稳定，可以跳过本节点普通战斗。",
    "weaknesses": [],
    "recommendedAction": "进入下一战斗节点",
    "suggestedRoomTypes": ["treasure", "battle"],
    "abilityDeltas": [
      {
        "abilityPointId": "ap-001",
        "delta": 3,
        "reason": "诊断题全对，基础语法能力小幅提升。"
      }
    ]
  }
}
```

规则：

- 只有 `correctRate == 1.0` 才触发 `battleBypassed=true`。
- 全对时后端直接完成该诊断节点和它绑定的战斗节点，结果记为 `diagnosis_perfect`。
- 非全对时必须进入战斗，但 AI 诊断报告仍然展示。

### 5.6 能力变化摘要

```http
GET /api/students/{studentId}/ability-deltas?course_id={courseCode}&run_id={runId}
```

返回最近通关导致的能力变化，用于 `StudentAbilityMapPanel.vue` 在图谱上显示“刚刚提升/下降/需补强”。

## 11. 风险与约束

- AI 不能直接决定数据库最终状态，必须由后端校验。
- 前端不能再自行推断解锁，否则刷新后状态会漂移。
- 诊断全对跳过战斗必须由后端完成，不应只在 `FloorView.vue` 里本地改 phase。
- 能力图谱不能只做前端平均，必须有后端变化记录。
- 旧接口要保留兼容，避免一次改动影响教师端或画像页。
- 路线重新生成要谨慎，active run 中已有通关记录时默认不覆盖。

## 12. 最小可展示版本范围

如果时间有限，优先完成以下闭环：

1. 后端规则生成动态路线，不接 AI 也可以先跑通。
2. 每个学生每门课持久化 active run。
3. 战斗通关解锁下一战斗和绑定辅助房间。
4. 诊断全对跳过战斗。
5. 地图显示 `locked/available/cleared/failed`。
6. 诊断报告先用规则兜底，AI 可用时增强。
7. 能力图谱至少显示通关后的掌握度变化和最近变化原因。

等这个闭环稳定后，再把路线数量、房间比例和诊断建议交给 AI 个性化生成。
