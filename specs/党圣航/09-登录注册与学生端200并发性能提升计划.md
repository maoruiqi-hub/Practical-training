# 登录注册与学生端 200 并发性能提升计划

## 1. 目标与约束

### 1.1 优化目标

本计划面向当前项目的登录、注册和学生端全链路并发能力提升，目标是在不修改现有功能、不修改现有前端页面展示与交互的前提下，让系统能够稳定通过并发数 200 的压测。

验收目标如下：

- 静态资源压测：并发 200，登录页及首屏 JS/CSS/图片请求失败率为 0。
- 登录接口：并发 200，持续 3 分钟，错误率为 0，P95 响应时间小于 500 ms。
- 注册接口：并发 200，使用唯一用户名/学号，错误率为 0；重复用户名场景应稳定返回业务失败，不出现 500 或数据库异常泄漏。
- 学生端核心流程：并发 200，持续 5 分钟，错误率小于 1%，P95 响应时间小于 2 s。
- 后端服务：压测期间无连接池耗尽、Tomcat 线程耗尽、数据库锁等待雪崩、JVM OOM。
- 页面与功能：Vue 页面模板、样式、路由展示、按钮流程、接口返回语义保持不变。

### 1.2 不修改范围

以下内容不作为本次优化修改对象：

- 不重做前端页面，不修改 Login/Register/学生端页面布局和样式。
- 不删除现有接口，不变更现有接口路径、参数含义和返回结构。
- 不调整用户可见业务流程，例如登录后跳转、学生端爬塔、题包获取、任务提交、错题查看等。
- 不以“跳过业务逻辑”换取压测结果。

允许修改的范围：

- 构建与部署方式，例如使用生产构建、Nginx 静态资源服务、关闭 source map 输出。
- 后端配置，例如 Tomcat 线程池、HikariCP 连接池、日志级别、压缩、超时。
- 后端内部实现，例如 SQL 聚合、批量查询、缓存、事务幂等、异步事件。
- 数据库索引、唯一约束、查询计划优化。
- 压测脚本与监控脚本。

## 2. 当前项目读后结论

### 2.1 项目结构

当前项目是前后端分离结构：

- 前端：`frontend`，Vue 3 + Vue CLI/Webpack + Element Plus + Axios。
- 后端：`backend`，Spring Boot 3.5 + MyBatis-Plus + Kingbase/PostgreSQL 兼容数据库。
- 前端接口基址：`frontend/src/api/index.js` 中 `baseURL: '/practical-training'`。
- 后端上下文路径：`backend/src/main/resources/application.yml` 中 `server.servlet.context-path: /practical-training`。

### 2.2 截图问题判断

截图中失败请求集中在：

- `GET /js/src_views_Login_vue.js`
- `GET /js/src_api_index_js.js`

错误为 `ConnectionAbortedError(10053)`，并且截图提示 Vue dev server 扛不住 50 并发压测，静态 JS 文件较大。

这说明当前压测有一部分直接打在 Vue 开发服务器上。`webpack-dev-server` 适合本地开发，不适合作为并发压测或生产静态资源服务器。它会携带热更新、source map、开发中间件等额外开销，连接池和文件传输能力都弱于 Nginx/Caddy/Apache/IIS。

结论：第一优先级不是改页面，而是改压测部署方式：前端必须使用生产构建产物，并由静态服务器承载。

### 2.3 登录注册链路现状

相关文件：

- `backend/src/main/java/com/neu/CoursePlatform/controller/StudentController.java`
- `backend/src/main/java/com/neu/CoursePlatform/service/impl/StudentServiceImpl.java`
- `backend/src/main/resources/mapper/StudentMapper.xml`
- `backend/src/main/resources/schema-kingbase.sql`

当前逻辑：

- 登录：`selectByUsername(username)` 查出学生，再在 Java 中比对密码。
- 注册：先 `selectByUsername(username)` 判断是否存在，再 `save(student)`。
- 数据库 schema 已有 `uk_student_username` 唯一索引声明。

主要并发风险：

- 实际数据库不一定已执行最新 schema，需要核验唯一索引是否真实存在。
- 注册的“先查再插”在并发下存在竞态，必须用数据库唯一约束兜底并捕获重复键异常。
- `SELECT *` 返回全字段，登录接口目前仍返回完整 Student 对象。为了不改功能，可以暂不缩减返回字段，但需要确保查询走唯一索引。

### 2.4 学生端高频接口现状

前端学生端 API 主要集中在：

- `/api/students/login`
- `/api/students/register`
- `/api/students/{studentNo}/assigned-tasks`
- `/api/tasks`
- `/api/tasks/{taskNo}`
- `/api/tasks/{taskNo}/submit`
- `/api/submissions/my`
- `/api/students/{studentNo}/progress`
- `/api/students/{studentNo}/stats`
- `/api/student/{studentNo}/course/{courseCode}`
- `/api/students/{studentNo}/mistakes`
- `/api/students/{studentId}/profile`
- `/api/students/{studentId}/tower-map`
- `/api/students/{studentId}/tower-run`
- `/api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/question-pack`
- `/api/students/{studentId}/ability-deltas`
- `/api/students/{studentId}/ability-radar`
- `/api/students/{studentId}/game-event`
- `/api/learning-logs`

代码阅读中发现的主要性能风险：

- `LearningProgressServiceImpl.buildStudentProgress` 会取学生所有提交和所有行为日志，再在 Java 中过滤/排序/截取。
- `StatsServiceImpl.buildStudentStats` 会对每条提交循环 `taskService.getById`，存在 N+1 查询。
- `TaskSubmissionServiceImpl.listDtoByTaskNo` 会对每条提交循环 `studentService.getById`，存在 N+1 查询。
- `TaskSubmissionServiceImpl.submitWithGrading` 在一次提交里串行完成查任务、查分配、计数、更新旧提交、保存答案、发布事件、更新状态。
- `AnalysisServiceImpl.buildCourseWrongStats` 会按课程任务循环查询答案，再在 Java 中聚合。
- `ProfileServiceImpl.listCourseStudentProfiles` 会全量查学生，并对每个学生查询画像、能力分、徽章，存在明显 N+1。
- `IncentiveServiceImpl.getLeaderboard` 会查询排行榜后对每个学生再查徽章数，存在 N+1。
- `TowerRunServiceImpl.getOrCreateActiveRun` 在 200 并发首次进入时可能同时生成多条 active run，需要数据库唯一约束和幂等重试。
- `TowerQuestionPackServiceImpl.getOrCreateQuestionPack` 同一节点并发请求时可能重复生成题包，需要唯一约束和幂等重试。
- 多处 AI/Agentic 调用可能进入同步请求链路，容易在并发下拖慢接口。
- `application.yml` 当前 Hikari 最大连接数为 20，对 200 并发偏小；MyBatis SQL stdout 日志在高并发下会显著拖慢接口。

## 3. 总体方案

整体优化分为六层推进：

1. 正确压测部署：前端生产构建，静态资源交给 Nginx/Caddy/IIS，后端只处理 API。
2. 运行时容量：调整 Tomcat、HikariCP、JVM、日志、压缩和超时。
3. 数据库索引：补齐学生端高频查询和并发幂等所需索引/唯一约束。
4. SQL 化与批量化：将 Java 内存过滤、N+1 查询和聚合改为数据库查询或批量查询。
5. 缓存与异步：课程知识点、能力点、题包、画像摘要等读多写少数据做短 TTL 缓存；行为事件和 AI 报告做异步或带超时降级。
6. 压测验收：分层压测静态资源、登录注册、学生端核心流程，并持续观察线程池、连接池、数据库和 GC。

## 4. P0：压测部署先修正

### 4.1 前端使用生产构建

执行：

```bash
cd frontend
npm run build
```

压测时只使用 `frontend/dist` 下的产物，不再压测 `npm run serve` 或 Vue dev server。

建议修改 `frontend/vue.config.js`，不改页面，仅改构建配置：

- `productionSourceMap: false`，避免生产产物输出 `.map`。
- 保留路由懒加载，不修改路由展示。
- 开启合理 `splitChunks`，减少单个首屏包过大。

注意：这属于构建优化，不是页面功能修改。

### 4.2 静态资源服务

推荐 Nginx 配置方向：

```nginx
server {
    listen 80;
    server_name _;

    root /path/to/frontend/dist;
    index index.html;

    gzip on;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;

    location /js/ {
        expires 30d;
        add_header Cache-Control "public, max-age=2592000, immutable";
        try_files $uri =404;
    }

    location /css/ {
        expires 30d;
        add_header Cache-Control "public, max-age=2592000, immutable";
        try_files $uri =404;
    }

    location /img/ {
        expires 30d;
        add_header Cache-Control "public, max-age=2592000, immutable";
        try_files $uri =404;
    }

    location /practical-training/ {
        proxy_pass http://127.0.0.1:8081/practical-training/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 3s;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

验收：

- 200 并发访问 `/login`、`/js/*.js`、`/css/*.css`，失败率为 0。
- 静态资源不再出现 `ConnectionAbortedError(10053)`。
- JS/CSS 响应头带 gzip 和长缓存。

## 5. P0：后端运行时容量配置

### 5.1 生产配置独立化

新增或调整生产 profile，例如 `application-prod.yml`，避免测试/开发配置进入压测：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 60
      minimum-idle: 15
      connection-timeout: 3000
      validation-timeout: 1000
      idle-timeout: 600000
      max-lifetime: 1800000
      leak-detection-threshold: 10000

server:
  tomcat:
    threads:
      max: 300
      min-spare: 30
    accept-count: 500
    max-connections: 10000
    connection-timeout: 10s
  compression:
    enabled: true
    mime-types: application/json,text/html,text/xml,text/plain,text/css,application/javascript
    min-response-size: 1024

logging:
  level:
    "[com.neu.CoursePlatform.mapper]": warn
    "[com.neu.CoursePlatform.controller]": info

mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.nologging.NoLoggingImpl
```

解释：

- 当前连接池最大 20，对 200 并发不足。建议先调至 60，再根据数据库承载能力微调。
- Tomcat 最大线程建议高于并发数，但不能无上限。300 线程足够覆盖 200 并发与少量慢请求。
- 禁止高并发下使用 `StdOutImpl` 打印 SQL，否则控制台 IO 会成为瓶颈。

### 5.2 JVM 启动参数

建议压测环境使用：

```bash
java -Xms512m -Xmx1024m -XX:+UseG1GC -jar backend/target/practical-training-backend-0.0.1-SNAPSHOT.jar --spring.profiles.active=prod
```

如机器内存充足可提高到 `-Xms1g -Xmx2g`。

验收：

- 200 并发下 Hikari active connection 不长期等于 maximum-pool-size。
- Tomcat busy threads 不长期等于 max threads。
- GC 无明显长暂停。

## 6. P0：数据库索引与唯一约束

### 6.1 登录注册索引

确认实际数据库存在：


### 6.3 行为日志索引

当前已有 `idx_user_time`，但要确认实际库存在。建议补齐：

```sql
CREATE INDEX IF NOT EXISTS idx_behavior_user_created
```

### 6.4 画像、排行榜、爬塔索引

```sql
CREATE INDEX IF NOT EXISTS idx_competency_student_course
    ON competency_score(student_no, course_code);

CREATE INDEX IF NOT EXISTS idx_achievement_student_course_type
    ON achievement(student_no, course_code, achievement_type);

CREATE INDEX IF NOT EXISTS idx_student_profile_course_exp
    ON student_profile(course_code, exp DESC);

CREATE INDEX IF NOT EXISTS idx_student_profile_course_coins
    ON student_profile(course_code, coins DESC);

CREATE UNIQUE INDEX IF NOT EXISTS uk_tower_active_run
    ON student_tower_run(student_no, course_code)

CREATE UNIQUE INDEX IF NOT EXISTS uk_tower_pack_run_node_mode
```

- `uk_tower_active_run` 是并发首次进入爬塔时的关键保护。
- 如果当前 Kingbase 版本不支持部分唯一索引，需要改为普通唯一键方案或新增 active 标记字段，但优先尝试 PostgreSQL 兼容部分索引。

## 7. P1：登录注册并发改造

### 7.1 登录接口

保持接口和返回不变，内部优化：

- `StudentMapper.selectByUsername` 确认走 `uk_student_username`。
- 可将 SQL 改为明确列名，避免 `SELECT *` 扫描不必要字段，但返回 Student 字段保持一致。
- 添加空用户名/空密码快速失败，减少无效 DB 查询。
- 登录成功写入 session 时只存必要用户对象或保持 Student 对象但避免额外大字段；当前 Student 较小，可先不改。

验收：

- 200 并发登录同一账号和不同账号均无 500。
- P95 小于 500 ms。

### 7.2 注册接口

保持注册功能不变，内部改造：

- `StudentServiceImpl.register` 改为事务方法。
- 仍可保留前置查询用于友好提示，但最终必须依赖数据库唯一约束。
- 捕获 `DuplicateKeyException`，返回业务失败。
- 对空用户名、空密码、空姓名快速失败。
- 注册成功后不自动登录，保持现有页面流程。

建议逻辑：

1. 参数校验。
2. 尝试插入。
3. 插入成功返回 true。
4. 唯一键冲突返回 false。

验收：

- 200 并发唯一用户注册成功率 100%。
- 200 并发重复用户名只有一个成功，其余稳定返回业务失败，不出现 500。

## 8. P1：学生端接口 SQL 化与批量化

### 8.1 任务列表与详情

涉及：

- `TaskAssignmentServiceImpl`
- `TaskAssignmentMapper.xml`
- `TaskController.detail`

优化：

- `selectAssignedTasks` 保持 join 查询，但确认使用 `idx_task_assignment_student_course_status`。
- `detail` 中 `getActiveAssignment` 使用复合索引。
- 对学生自己的任务列表可增加短 TTL 缓存，key 为 `studentNo + courseCode + taskType + status + lessonNo`，TTL 30 秒，任务提交/分配变更时清理。

验收：

- 200 并发学生任务列表 P95 小于 1 s。

### 8.2 任务提交

涉及：

- `TaskSubmissionController.submit`
- `TaskSubmissionServiceImpl`
- `TaskSubmissionMapper.xml`

优化：

- `supersedePrevious` 改为单条 SQL 批量更新，不逐条 select 再 update。
- `countByStudentAndTask` 走 `idx_task_submission_student_task_status_time`。
- 自动判题中对题目使用批量查询，不在每个答案上 `questionService.getById`。
- 保存 `SubmissionAnswer` 继续批量 `saveBatch`。
- `publishAssessmentResultEvents` 改为事务提交后异步执行，避免学生提交请求等待画像/楼层/事件联动。
- `attemptCount` 不再每个答案查询历史答案；改为批量聚合或从本次上下文传入。
- 对同一学生同一任务并发提交使用事务和行级锁，避免提交次数突破 `maxAttempts`。

验收：

- 200 并发提交不同学生任务，无数据库死锁。
- 同一学生重复并发提交，最多写入允许次数，返回业务失败而非 500。

### 8.3 我的提交、学生课程统计、进度

涉及：

- `TaskSubmissionController.listMy`
- `StatsServiceImpl`
- `LearningProgressServiceImpl`

优化：

- `listByStudentNo` 增加按时间倒序与分页/限制能力；页面当前如需全量可保持默认，但学生端统计接口内部应只取必要字段。
- `buildStudentStats` 批量加载 task 信息，替代循环 `taskService.getById`。
- `buildStudentCourseStats` 在 SQL 中按 `student_no + course_code` 统计，不全量取学生所有提交后 Java 过滤。
- `buildStudentProgress` 的行为日志时间线改为 SQL `LIMIT 10`，不再取所有日志后 stream limit。
- 课程进度接口 `buildCourseProgress` 是教师端为主，但如果学生端页面触发，也要避免 `studentService.list()` 全量学生和每个学生 `getById` 的 N+1，改为 join 聚合。

验收：

- `/api/students/{studentNo}/progress` 200 并发 P95 小于 1.5 s。
- `/api/students/{studentNo}/stats` 200 并发 P95 小于 1.5 s。

### 8.4 错题与学情分析

涉及：

- `AnalysisServiceImpl`
- `SubmissionAnswerServiceImpl`

优化：

- 学生错题 `buildStudentWrongStats` 保持返回结构，但底层查询要使用组合索引。
- 课程错题 `buildCourseWrongStats` 改为一次 join 查询，不按课程任务循环查询答案。
- `knowledgeName` 不在聚合每项中反复 `knowledgePointService.getById`，改为批量加载知识点名称映射。
- 大结果 `wrongList` 增加内部限制或分页兼容策略；如果必须保持旧接口全量返回，至少按学生/课程加索引并限制压测数据量。

验收：

- `/api/students/{studentNo}/mistakes` 200 并发 P95 小于 2 s。

## 9. P1：学生画像、排行榜、推荐

### 9.1 画像摘要

涉及：

- `ProfileApiController.profile`
- `ProfileServiceImpl.getProfileSummary`
- `ProfileServiceImpl.getOrCreateProfile`

优化：

- `getOrCreateProfile` 增加事务与唯一约束冲突重试。并发首次进入时，如果多个请求同时创建画像，只有一个 insert 成功，其余捕获重复键后 reselect。
- `getProfileSummary` 中能力点、能力分、能力图谱按课程做短 TTL 缓存，学生分数按学生课程做短 TTL 缓存。
- 缓存 TTL 建议 30 秒到 2 分钟，答题/通关/成长变更后清理学生课程缓存。

验收：

- 并发首次访问同一学生画像，不产生重复 profile，不出现 500。

### 9.2 推荐生成

涉及：

- `RecommendationServiceImpl.generateRecommendations`
- `ProfileApiController.recommendations`

风险：

- `recommendations` GET 在推荐为空时会同步调用 `generateRecommendations`。
- `generateRecommendations` 每个能力点都会调用 `AgenticClient`，并发下会放大外部 AI 延迟。

优化：

- GET 优先返回已有推荐。
- 如果为空，使用本地 fallback reason 立即生成或返回基础推荐，同时异步刷新 AI reason。
- Agentic 调用增加连接池、超时、熔断和并发上限。
- 同一学生课程推荐生成加互斥锁或唯一任务标记，避免 200 并发重复生成。

验收：

- AI 服务慢或不可用时，学生端推荐接口不拖垮整个系统，仍返回业务可用结果。

### 9.3 排行榜

涉及：

- `IncentiveServiceImpl.getLeaderboard`

优化：

- 使用 SQL 一次查询前 20，并 left join/聚合徽章数量。
- 避免排行榜每个 profile 再查一次 `getAchievements`。
- 对 `courseCode + type` 做 30 秒缓存。

验收：

- `/api/leaderboard` 200 并发 P95 小于 1 s。

## 10. P1：爬塔、题包、雷达图

### 10.1 active run 幂等

涉及：

- `TowerRunServiceImpl.getOrCreateActiveRun`
- `TowerRunServiceImpl.generateRun`

优化：

- 数据库加 `uk_tower_active_run(student_no, course_code) WHERE status='active'`。
- `getOrCreateActiveRun` 并发下先查，生成时如遇唯一键冲突，重新查询已有 active run 并返回。
- `generateRun(force=false)` 必须是幂等的，不允许并发生成多个 active run。
- `generateRun(force=true)` 保持现有功能，但归档旧 run 与插入新 run 必须在事务内完成。

验收：

- 200 并发同时进入同一学生同一课程爬塔，只保留 1 条 active run。

### 10.2 节点 DTO 与支撑索引缓存

涉及：

- `TowerRunServiceImpl.toRunDto`
- `TowerRunServiceImpl.supportIndexes`

优化：

- `supportIndexes(courseCode)` 当前会加载知识点和能力点，可按课程缓存 1 分钟。
- 同一次请求内只构建一次索引，传入 `toNodeDto`。
- 知识点和能力点变更时清理课程缓存。

验收：

- `/api/students/{id}/tower-run` 200 并发 P95 小于 1.5 s。

### 10.3 题包并发与批量查题

涉及：

- `TowerQuestionPackServiceImpl.getOrCreateQuestionPack`
- `TowerQuestionPackServiceImpl.regenerateQuestionPack`

优化：

- 数据库加唯一键 `uk_tower_pack_run_node_mode`。
- 同一 `runId + nodeId + mode` 并发请求只生成一个题包；其他请求捕获唯一键冲突后 reselect。
- `toDto(pack)` 中根据 question ids 批量查询题目，不逐个 `questionService.getById`。
- `layeredCandidates` 中题目候选按课程/知识点缓存短 TTL，题库变更后清理。
- `recentUsedQuestionIds` 和 `runUsedQuestionIds` 查询使用新增索引。

验收：

- 200 并发同时请求同一节点题包，不重复生成，不报 500。

### 10.4 通关、诊断、雷达图

涉及：

- `TowerRunServiceImpl.completeNode`
- `TowerRunServiceImpl.diagnoseNode`
- `AbilityRadarServiceImpl.getAbilityRadar`

优化：

- 通关结算中 AI 诊断报告必须有超时和降级，不让外部 AI 阻塞接口超过阈值。
- 对同一节点重复完成使用状态判断和幂等处理，避免重复插入 delta/attempt。
- `AbilityRadarServiceImpl.currentScores` 与 ability list 批量查询并缓存。
- `deltaIndex` 使用组合索引。

验收：

- AI 不可用时，通关接口仍可完成业务结算，返回降级报告状态。

## 11. P1：行为日志与事件链路

### 11.1 行为日志

涉及：

- `BehaviorLogController.record`
- `BehaviorLogServiceImpl`
- `BehaviorLogMapper.xml`

优化：

- 写日志保持单次 insert。
- 查询日志增加 SQL limit，学生进度时间线只取最近 10 条。
- 学生端高频行为日志写入如压力过大，可使用有界队列异步批量落库；队列满时保留核心业务，降级丢弃非关键日志或返回业务成功但记录降级日志。

验收：

- 高频学习行为上报不拖慢页面核心接口。

### 11.2 事件发布

涉及：

- `SpringGameEventPublisher`
- `TaskSubmissionServiceImpl.publishAssessmentResultEvents`
- `ProfileGameEventListener`

优化：

- 事务内只写核心提交数据。
- 事件发布放在事务提交后异步执行。
- 事件执行线程池设定有界队列和拒绝策略，避免 200 并发下无限堆积。
- 事件处理失败记录日志，不影响学生提交接口成功返回。

验收：

- 任务提交接口不因画像/楼层/风险事件处理慢而超时。

## 12. P2：前端请求层非页面优化

不修改页面模板和样式，只在请求层/构建层优化：

- 保持 `src/views/*.vue` 页面不动。
- 保持路由懒加载。
- `api/index.js` 可增加相同 GET 请求短时间去重，避免同一页面组件同时发起重复请求；必须确保返回数据结构不变。
- 对 30 秒内不变的课程配置、能力图谱、知识点图谱等读接口，可在请求层或后端缓存。
- Axios timeout 当前 30 秒可保留；后端优化后不应依赖长 timeout。

注意：如果压测严格要求“不改前端源码”，则只做生产构建、source map、Nginx 缓存，不做 Axios 去重。

## 13. 压测方案

### 13.1 基线压测

先记录当前基线，禁止一上来只看最终结果：

- 静态资源：登录页、主 JS、chunk-vendors、CSS、图片。
- API：登录、注册、学生任务列表、学生进度、学生统计、错题、画像、爬塔 run、题包。
- 数据库：慢 SQL、连接数、锁等待。
- 后端：Tomcat busy threads、Hikari active/idle/pending、JVM heap、GC。

### 13.2 静态资源压测

场景：

- 200 并发访问 `/login`。
- 200 并发访问生产构建后的最大 JS 文件。
- 持续 3 分钟。

通过标准：

- 失败率 0。
- P95 小于 300 ms。
- 无 `ConnectionAbortedError(10053)`。

### 13.3 登录压测

场景：

- 200 并发学生登录。
- 账号可使用同一测试账号，也可使用 200 个不同账号。
- 每个虚拟用户保持 cookie/session。

通过标准：

- HTTP 失败率 0。
- 业务 code 成功率符合账号数据预期。
- P95 小于 500 ms。

### 13.4 注册压测

场景 A：唯一用户注册。

- 200 并发，每个 VU 使用唯一 username/studentNo。
- 期望全部成功。

场景 B：重复用户名注册。

- 200 并发使用同一 username。
- 期望只有一个成功，其余业务失败，无 500。

### 13.5 学生端核心流程压测

每个 VU 执行：

1. 登录。
2. 获取学生任务列表。
3. 获取学生进度。
4. 获取学生统计。
5. 获取错题。
6. 获取画像。
7. 获取 tower-run。
8. 获取当前节点题包。
9. 上报一次学习行为。

通过标准：

- 持续 5 分钟，并发 200。
- HTTP 失败率小于 1%。
- 登录 P95 小于 500 ms。
- 普通 GET P95 小于 1.5 s。
- 题包/画像/错题 P95 小于 2 s。

### 13.6 写接口压测

谨慎压测，避免污染正式数据：

- 注册使用测试前缀账号。
- 提交任务使用测试任务和测试学生。
- 通关/诊断使用测试 run。

通过标准：

- 无唯一键异常泄漏为 500。
- 数据状态符合幂等预期。

## 16. 风险与应对

### 16.1 数据库承载不足

如果 Hikari 调到 60 后数据库 CPU/连接数顶满，不能继续盲目加连接池。应先看慢 SQL 和索引命中，再调整连接池。

### 16.2 AI 外部服务拖慢

推荐、诊断、报告类 AI 调用必须有限流、超时和降级。并发 200 时不能让外部 AI 决定核心学生端是否可用。

### 16.3 缓存导致数据短暂不一致

只对读多写少、短时间允许延迟的数据做短 TTL 缓存。任务提交、注册、登录、通关结算等强一致写接口不直接用缓存跳过数据库。

### 16.4 压测数据污染

注册、提交、通关压测必须使用测试账号、测试课程、测试任务，并提供清理 SQL。

## 18. 判断标准

本次优化不能只以“压测不报错”为结束标准。必须同时满足：

- 静态资源由生产静态服务器承载，不再使用 Vue dev server 压测。
- 登录注册通过 200 并发。

- 代码没有删除或跳过业务功能。
- 前端页面展示和用户流程保持不变。
- 数据库没有重复 active run、重复题包、异常重复注册等并发脏数据。
- 慢 SQL、连接池、线程池、GC 指标可解释并稳定。
