# 诊断奖励异步、奖励页能力雷达与题包真实化修复计划

## 1. 背景与当前判断

这次要集中修复三个体验问题：

1. 诊断房全对后，跳到奖励页前会卡一段时间。
2. 奖励页右侧仍展示“图谱上下文”，但期望展示能力雷达图谱。
3. 诊断房和战斗房遇到的题目看起来仍是之前那几道，没有体现“每个关卡题目不同”。

我对当前代码和数据库做了只读核对，结论如下：

- `FloorView.vue#handleDiagnosed` 现在会 `await diagnoseTowerNode(...)`，后端诊断报告和能力变化都完成后才 `phase='reward'`。如果后端 AI 诊断慢，前端就会卡在诊断房。
- 奖励页阶段 `phase='reward'` 时，右侧 `intel-dock` 仍然挂的是 `KnowledgeContextPanel`，所以看到的是前置/后继知识点，不是能力雷达。
- 数据库 `question` 表里课程 `1` 有 85 道题、17 个知识点，每个知识点 5 道题。
- 截图里的 `将字符串"123"转换为整数的表达式是____` 是数据库题目，属于 `course_code=1, knowledge_point_id=3`，并不是前端 fallback 假题。
- 当前“题目没变”的主要原因不是没读数据库，而是：
  - 同一个知识点只有 5 道题，诊断 3 道、战斗 5 道，很容易重复。
  - `getOrCreateQuestionPack` 会复用已有题包，旧题包不主动刷新。
  - 推荐算法只按当前知识点优先，没有把“同一 run 内已出现题目不得重复”作为硬约束。
  - 题池不足时只简单扩展到课程题库，没有优先扩展到前置/后继/同能力点知识点。

## 2. 任务一：诊断全对后先跳奖励页，诊断报告异步加载

### 2.1 目标

诊断房最后一题答完后，如果本地判断全对，立即进入奖励页，不再等待 AI 诊断报告或后端完整同步。

右侧诊断结果如果还没回来，显示：

- “诊断结果生成中”
- 骨架屏/加载状态
- 已知的本地正确率 100%

AI 报告回来后，再替换成真实诊断报告、能力变化说明和推荐动作。

### 2.2 当前卡顿点

文件：

- `frontend/src/views/FloorView.vue`

当前逻辑：

```js
const res = await diagnoseTowerNode(...)
if (payload.battleBypassed) {
  await refreshProfile()
  phase.value = 'reward'
}
```

问题：

- `diagnoseTowerNode` 后端会生成诊断报告，可能调用 AI。
- `refreshProfile` 也会增加一次等待。
- `phase='reward'` 放在这些等待之后，所以 UI 卡住。

### 2.3 修改方案

新增状态：

```js
const diagnosisSyncing = ref(false)
const diagnosisSyncError = ref('')
const diagnosisSyncPromise = ref(null)
```

调整流程：

```text
DiagnosisRoom finish
  -> 本地判断 perfect
  -> 立即设置 battleResult = { cleared: true, diagnosisBypass: true, pendingReport: true }
  -> 立即 phase = 'reward'
  -> 后台调用 diagnoseTowerNode
  -> 返回后更新 diagnosisResult.report / run / profile / radar
  -> 失败时右侧显示“同步失败，可返回地图后重试/刷新”
```

核心规则：

- 只有本地 `correctCount === questions.length` 才允许乐观跳奖励页。
- 非全对仍等待后端诊断返回，再进入战斗。
- 后端仍是最终事实源：节点通关、能力变化、解锁以后端返回为准。
- 奖励选择不应被诊断报告阻塞；但进入结算时如果后端同步还没完成，结算页显示“通关记录同步中”。

### 2.4 前端展示

右侧 Diagnosis 区域：

```vue
<div v-if="diagnosisSyncing">
  <el-skeleton animated />
  <p>诊断报告生成中，奖励选择可先继续。</p>
</div>
```

奖励页顶部可显示：

- `诊断全对，战斗已跳过`
- `AI 诊断报告生成中...`

### 2.5 验收

- 诊断全对最后一题后，1 秒内切到奖励页。
- AI 慢时不会卡在诊断房。
- AI 报告回来后右侧内容自动更新。
- 后端失败时有非阻塞提示，不出现白屏或无限等待。

## 3. 任务二：奖励页右侧改为能力雷达图谱

### 3.1 目标

奖励页右侧不再展示 `KnowledgeContextPanel`，改为展示之前要求的能力雷达图谱，即：

- 通关前能力曲线
- 通关后能力曲线
- 本次变化最大的能力点
- 变化原因/AI 总结

### 3.2 当前问题

文件：

- `frontend/src/views/FloorView.vue`
- `frontend/src/components/KnowledgeContextPanel.vue`
- `frontend/src/components/StudentAbilityMapPanel.vue`

当前 `FloorView.vue` 的右侧固定渲染：

```vue
<KnowledgeContextPanel
  :course-id="courseId"
  :knowledge-point-id="kpId"
/>
```

所以在奖励页仍然是知识图谱上下文。

### 3.3 修改方案

在 `FloorView.vue` 里按 phase 切换右侧内容：

```vue
<AbilityRadarPanel
  v-if="phase === 'reward' || phase === 'settlement'"
  :student-no="studentId"
  :course-code="courseId"
  :run-id="runId"
  :node-id="nodeId"
  :loading="diagnosisSyncing || abilityRadarLoading"
/>

<KnowledgeContextPanel
  v-else
  :course-id="courseId"
  :knowledge-point-id="kpId"
/>
```

优先复用已有 `StudentAbilityMapPanel.vue` 的雷达逻辑，但建议拆成两个组件：

- `AbilityRadarChart.vue`：只负责 ECharts 雷达。
- `StudentAbilityMapPanel.vue`：画像页完整能力图谱。
- `FloorAbilityRadarPanel.vue`：战斗/奖励页右侧紧凑版。

### 3.4 API

复用已存在接口：

```http
GET /api/students/{studentId}/ability-radar?course_id={courseCode}&run_id={runId}&node_id={nodeId}
```

诊断报告还没回来时：

- 先显示本地 `battleResult.correctRate`。
- 雷达区域 skeleton。
- 后端完成后重新拉取 radar。

### 3.5 验收

- 奖励页右侧显示能力雷达，而不是前置/后继知识点。
- 诊断全对跳过战斗后，也能看到能力变化。
- 雷达加载中有明确 loading 状态。
- 结算页保留雷达摘要。

## 4. 任务三：题包真实个性化，保证每关题目不同

### 4.1 数据库事实

只读核对结果：

```text
course_code=1
questions=85
knowledge_points=17
每个 knowledge_point_id 约 5 道题
```

示例：

```text
knowledge_point_id=3
【Python基础语法与数据类型】将字符串"123"转换为整数的表达式是____。
【Python基础语法与数据类型】解释Python中缩进的语法意义...
```

所以当前截图里的题目确实来自数据库。但因为单知识点题池只有 5 道，如果每关只绑定一个知识点，诊断 3 道、战斗 5 道必然高度重复。

### 4.2 当前题包逻辑问题

文件：

- `backend/src/main/java/com/neu/CoursePlatform/service/impl/TowerQuestionPackServiceImpl.java`
- `frontend/src/components/DiagnosisRoom.vue`
- `frontend/src/components/BattleRoom.vue`

当前后端：

```java
getOrCreateQuestionPack(...)
  -> 如果已有 pack，直接返回旧 pack
  -> 没有 pack 才 regenerate
```

当前选择：

- 优先 `course + current knowledgePointId`
- 不足时扩展到整门课
- 没有强制排除当前 run 已经出现过的题
- 没有根据诊断/战斗模式做不同题池分层
- 没有把前置/后继/同能力点作为优先扩展范围

### 4.3 修改目标

每个关卡题目必须满足：

1. 优先来自数据库 `question` 表。
2. 同一 `run_id` 下，不同 `node_id` 的题包尽量不重复。
3. 诊断房和战斗房的题包不同。
4. 当前知识点题不足时，按顺序扩展：
   - 当前知识点
   - 同能力点绑定的知识点
   - 知识图谱前置/后继知识点
   - 同课程其他知识点
5. 已经做过的题降权，当前 run 已出现题硬排除；除非题量实在不足。
6. 旧题包如果是旧策略生成，要自动失效或允许一键重生成。

### 4.4 后端修改方案

#### 4.4.1 增加题包策略版本

在 `student_tower_question_pack.strategy_json` 中加入：

```json
{
  "strategyVersion": 2,
  "poolPolicy": "kp-ability-graph-course",
  "excludeRunUsed": true
}
```

`getOrCreateQuestionPack` 读取旧 pack 时：

- 如果没有 `strategyVersion=2`，不复用，直接重生成。
- 如果 pack 中 questionIds 少于目标数量，重生成。
- 如果 questionIds 已经和其他 node 高度重复，重生成。

#### 4.4.2 查询当前 run 已用题

新增方法：

```java
Set<String> runUsedQuestionIds(String runId, String exceptNodeId)
```

来源：

- `student_tower_question_pack.question_ids_json`
- `student_tower_attempt.answer_summary_json`

规则：

- 当前 node 的旧 pack 可忽略。
- 其他 node 的题优先硬排除。

#### 4.4.3 构建分层候选池

新增：

```java
List<Question> buildLayeredCandidatePool(StudentTowerRun run, StudentTowerNode node, String mode)
```

候选层级：

1. `currentKpQuestions`
2. `sameAbilityQuestions`
3. `graphNeighborQuestions`
4. `courseFallbackQuestions`

每道题加元信息：

```json
{
  "questionId": "8",
  "poolLayer": "current_kp",
  "alreadyUsedInRun": false,
  "recentlyAnswered": true,
  "difficultyGap": 0
}
```

#### 4.4.4 诊断和战斗分题型

诊断房：

- 3 题。
- 优先 `single/fill`。
- 覆盖概念确认，难度 1-3。

战斗房：

- 普通战斗 5 题。
- 普通战斗只允许当前节点知识点题目，不从其他章节补题。
- 至少 2 种题型。
- 难度跟 `node.difficulty` 匹配。

精英/Boss：

- 6/8 题。
- 覆盖多个知识点。
- 更高难度和综合题。

精英战固定配额：

- 3 题：当前节点知识点。
- 2 题：当前知识点所属能力点下的其他知识点。
- 1 题：学生真实历史答错题或历史薄弱知识点题。
- 历史证据或同能力点题池不足时，只能从当前知识点、同能力点和真实历史薄弱题池补位，并在题包策略中返回 `quotaFallback=true`；不得从任意课程章节静默补题。

Boss 战使用课程综合题池，允许跨知识点选题。

#### 4.4.5 增加调试字段

题包 API 返回：

```json
{
  "packId": "...",
  "strategy": {
    "strategyVersion": 2,
    "candidateCount": 18,
    "currentKpCount": 5,
    "sameAbilityCount": 10,
    "excludedRunUsedCount": 8,
    "expandedToCourse": true
  },
  "questions": []
}
```

前端开发时可以快速判断是否真的换题。

### 4.5 前端修改方案

#### 4.5.1 不再静默 fallback 到旧题

现在如果题包接口失败，组件会继续走旧 `getTaskQuestions/getQuestionsByKnowledgePoint`，用户看起来就像“题包没生效”。

调整为：

- 有 `runId + nodeId` 时，题包接口失败要显示错误状态和“重试/重生成题包”。
- 不再静默退回旧任务题。
- 只有非爬塔入口才走旧题库接口。

#### 4.5.2 展示题包来源

开发/展示版本可在角落显示：

```text
题包：数据库推荐 · 5题 · 已避开本轮重复题
```

便于现场确认不是前端固定题。

#### 4.5.3 增加重生成入口

在诊断/战斗房 loading 失败或调试按钮里调用：

```http
POST /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/question-pack/regenerate?mode=battle
```

### 4.6 验收

- 进入不同 node，返回不同 `packId`。
- 同一 run 下，两个不同 battle node 的 `questionId` 不完全相同。
- 诊断房 3 题和战斗房 5 题不完全相同。
- 题包 API 返回的 `questions[*].stem` 能在数据库 `question` 表查到。
- 题库足够时，不再出现组件 fallback 演示题。
- 如果当前知识点只有 5 题，第二个相关关卡会自动扩展到同能力点或邻近知识点，而不是重复同 5 题。

## 5. 推荐实施顺序

### 第一阶段：先修用户可感知卡顿

1. 改 `FloorView.vue#handleDiagnosed`，诊断全对先 `phase='reward'`。
2. 增加 `diagnosisSyncing/diagnosisSyncError`。
3. 右侧诊断报告 loading 化。
4. 验证 AI 慢时不会卡在诊断房。

### 第二阶段：奖励页换能力雷达

1. 抽出 `AbilityRadarChart.vue`。
2. 新增 `FloorAbilityRadarPanel.vue`。
3. `FloorView.vue` 在 reward/settlement 阶段右侧显示雷达。
4. 诊断报告返回后刷新雷达。

### 第三阶段：题包真实换题

1. 后端题包策略升级到 `strategyVersion=2`。
2. 增加 run 级题目去重。
3. 增加同能力点/知识图谱邻居扩展题池。
4. 前端爬塔入口禁止静默 fallback 旧题。
5. 增加题包调试信息和重生成入口。

## 6. 最小可交付范围

本次最少要做到：

- 诊断全对后立即进入奖励页。
- 诊断报告未返回时右侧显示 loading。
- 奖励页右侧显示能力雷达，而不是知识图谱上下文。
- 同一 run 下不同关卡题包不完全相同。
- 爬塔房间题包失败时不再偷偷显示旧题，而是提示题包加载失败。

## 7. 风险点

- 如果后端诊断同步失败，但用户已经选了奖励，需要避免重复发奖或状态不一致。建议奖励选择照常进行，但结算页显示“节点通关同步待确认”，并提供重试同步。
- 当前每个知识点只有 5 道题，想做到每个关卡完全不重复，必须允许扩展到同能力点/邻近知识点。
- 如果旧 `student_tower_question_pack` 已缓存旧策略，需要通过 `strategyVersion` 自动失效，否则刷新后仍会看到旧题。
- 如果前端仍保留静默 fallback，用户会误以为后端推荐无效，所以爬塔入口必须把题包失败显性化。
