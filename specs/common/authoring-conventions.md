# 规格文档写作规范（如何写/扩充本 spec）

> 一句话定位：规定本 `specs/` 里**文档本身**怎么写、怎么扩充，保证新增/修改的规格与既有风格一致、可被团队成员稳定消费。写或改任何 spec 文档前，先读本篇。
> 阅读前置：[`../README.md`](../README.md)

---

## 1. 通用排版

- **语言**：中文。**格式**：Markdown。
- **每篇顶部三件套**：
  ```
  > 一句话定位：<这篇文档是干什么的>
  > 阅读前置：[<必须先读的文档>](相对链接)
  > 状态：草拟 / 待审 / 已批准
  ```
- **表格 + Mermaid 驱动**：能用表/图说清的，不写大段话。流程图用 Mermaid，数据关系用表格。
- **相对链接**：跨文档引用一律相对路径（如 `../docs/architecture/模块接口与协作规范.md`），便于校验无死链。
- **声明边界**：需求文档只写"要做什么"，不写"怎么实现"；设计文档明确"只含设计原理，不含代码实现"。
- **用人话，不生造术语**：软件工程里没有的名词不要造。首次出现的领域术语，加一句解释。
- **不复制旧文档原文**：吸收参考资料时重写为权威表述，可脚注出处（如"参考token_reduce项目"）。

### 1.1 表格规范

表格应有表头行和分隔行，对齐使用 `|` 分隔：

```markdown
| 列1 | 列2 | 列3 |
|------|------|------|
| 数据 | 数据 | 数据 |
```

## 2. EARS 需求句式（所有需求文档专用）

需求一律用 EARS（Easy Approach to Requirements Syntax），**编号化、可追溯、可单测**。

### 2.1 五种句式

| 模式 | 句式 | 用于 |
|------|------|------|
| 普遍（Ubiquitous） | `系统应 <响应>` | 恒常要求，不依赖任何条件 |
| 事件驱动（Event-driven） | `当 <触发事件> 时，系统应 <响应>` | 某输入/事件发生时 |
| 状态驱动（State-driven） | `在 <状态> 期间，系统应 <响应>` | 处于某系统状态期间 |
| 非期望（Unwanted） | `如果 <异常条件>，则系统应 <响应>` | 异常/边界/错误处理 |
| 可选特性（Optional） | `若 <特性存在>，系统应 <响应>` | 条件性能力/功能开关 |

### 2.2 编号规则

每条需求有**唯一编号**，格式 `R<组>.<序>`，按能力分组：

```
R1.1  课程信息管理 → 创建课程
R1.2  课程信息管理 → 修改课程
R2.1  知识图谱 → 知识点提取
R2.2  知识图谱 → 知识图谱可视化
...
```

**`R` 编号一旦分配，不要更改**。新增需求在组末追加，不插入中间打乱编号。

### 2.3 示例

```markdown
# 课程信息管理需求

## R1 组：课程基本信息管理

**R1.1** 教师登录后，系统应允许创建新课程，录入课程名称、课程编号、学分、学时。

**R1.2** 当教师修改课程信息时，系统应保存修改记录并展示修改时间。

**R1.3** 在课程有已选课学生期间，系统不应允许删除该课程；应先提示教师联系学生退课。

**R1.4** 如果课程编号与已有课程重复，则系统应拒绝创建并提示"课程编号已存在"。
```

### 2.4 规则

- 一条需求只说一件可验证的事。
- 含糊词（"高效""合理""友好""快"）要换成可检验条件：
  - ❌ "系统应快速响应" → ✅ "系统应在 2 秒内返回查询结果"
  - ❌ "界面应友好" → ✅ "核心功能 ≤3 步可完成"
- 正向需求写完后，明确写否定需求（`系统不应 …`）标出越权红线。

## 3. 需求文档基本格式

每份需求/规格文档至少包含以下小节：

| 小节 | 内容 | 要求 |
|------|------|------|
| **背景** | 为什么需要这个功能 | 让没上下文的人也看懂动机 |
| **目标** | 要达到什么效果 | 明确的、可检验的 |
| **功能描述** | 用 EARS 句式写具体做什么 | 每条带 R 编号 |
| **验收标准** | 怎样算"做完了" | 可客观检验的条件列表 |
| **技术约束** | 平台、框架、兼容性等限制 | 有则写，无则写"无特殊约束" |
| **不做（明确排除）** | 明确不做什么 | 防止范围蔓延 |

## 4. design.md 写法（docs/ 下的设计文档）

> 设计文档不属于 specs/，但写作时遵循同样的排版纪律。

- 开头 Mermaid 数据流（输入→各模块→输出）或 ASCII 架构图。
- **数据结构/字段**引用 `docs/architecture/` 或 `docs/data-model/` 的**权威定义**，不在 design 里重复定义同一字段。
- 算法用**伪代码层**表达（可读、可转测试），不贴实现代码。
- 给"落点建议"（哪个目录/模块），但注明"最终以实现为准"。
- 列**"不做（明确排除）"**小节。

## 5. tasks.md / 实施计划写法（docs/plans/ 下）

> 详见 [`../../docs/plans/plan-writing-guide.md`](../../docs/plans/plan-writing-guide.md)。

每个任务统一格式：

```markdown
- [ ] **T<n> — <动词短语>**（满足 R<…>, R<…>）
  - 验收：<完成时必须为真的可检条件，≤3 条>
  - 验证：<可执行命令，如 pytest -k xxx>
  - 依赖：<前置任务号，或"无">
  - 文件：<将改动的目录/文件，≤~5>
  - 规模：XS / S / M / L
```

规则：
- **每条回引需求编号**（保证 spec → plan → 代码可追溯）。
- 任务按**依赖顺序**排，不按重要性。
- 单任务**改动 ≤ ~5 文件**、可在一个专注 session 完成。
- 阶段间设检查点；末尾给该 milestone 的"完成定义（DoD）"。

## 6. 诚实纪律（写进文档的硬要求）

- **不说"很好""高效""合理"** 这种无法检验的词。换成可度量的标准。
- **承认不确定性**：暂时确定不了的技术决策，明确标 `[待定]`，不假装已确定。如：
  ```markdown
  前端框架：[待定] 候选 React / Vue，待团队讨论后确定
  ```
- **写边界，不写实现**：specs 只写"要什么"，不规定"用什么框架/算法实现"。
- **引用权威来源**：参考外部文档时给链接或脚注，不转述可能过时的内容。
- **每个判定带理由**：不说"显然应该选A"，说"选A，因为B/C/D条件限制下A是唯一可行方案"。

### 6.1 可检验性自检

写完一条需求，问自己：

> "另一个人能客观判断这条需求有没有被满足吗？"

如果不能 → 需求还不够具体，继续细化。

## 7. 文件命名

- 用中文描述性命名，一眼看出内容：`创新点-数据库.md`、`详细设计说明书.md`
- 同一主题多个文件用数字前缀：`01-需求分析.md`、`02-设计方案.md`
- 不要用空格或特殊字符（`/ \ : * ? " < > |`），用 `-` 或 `_` 替代

## 8. 新增一篇 spec 的清单

- [ ] 顶部"一句话定位 + 阅读前置 + 状态"齐全。
- [ ] 需求用了 EARS 句式并编号（`R<组>.<序>`）。
- [ ] 背景/目标/功能描述/验收标准/技术约束/不做 六小节齐全。
- [ ] 有"不做（明确排除）"小节。
- [ ] 跨文档用相对链接（不硬编码绝对路径）。
- [ ] 诚实表述：不虚报、不假装确定、不确定项标 `[待定]`。
- [ ] 文件命名符合规范，放在正确的个人/主题目录下。
- [ ] 更新 `specs/README.md` 路线表。
