### 阶段一修复说明

`KnowledgePointServiceImpl` 生产代码使用 MyBatis-Plus `LambdaQueryWrapper` / `QueryWrapper` 构造查询条件，业务逻辑本身较直接：

- `listByCourse` 按课程、课时、关键词过滤。
- `listByCourseCode` 按课程、章节过滤。
- `removePoint` / `deleteWithDependencies` 删除前检查是否被题目引用。

失败原因是测试中的 Mapper proxy 没有正确解析 MyBatis-Plus wrapper 条件，导致：

1. `selectList` 的过滤条件没有生效。
2. `questionService.count(...)` 的 wrapper 参数没有被 mock 正确识别。

本次修复只改测试代码，不改生产代码。修复点：

1. 在 `KnowledgePointServiceImplTest` 中使用 `TableInfoHelper.initTableInfo(...)` 初始化 MyBatis-Plus 实体元数据，使 `LambdaQueryWrapper` 能生成真实 SQL 片段。
2. 修正 fake mapper 的 SQL 条件解析逻辑，先移除外层括号和 `ORDER BY` 等尾部子句，再拆分 `AND` / `OR`。
3. 在 `QuestionService.count(...)` mock 中先触发 `wrapper.getSqlSegment()`，确保 `QueryWrapper` 参数落入 `paramNameValuePairs` 后再判断题目引用。

当前 `backend/pom.xml` 已配置 `jacoco-maven-plugin`，并在阶段四新增了 `jacoco:check` 规则：

- 核心功能 100% 和辅助功能 80% 的细分验收仍需要结合 `jacoco.xml` 分类统计。

后续建议继续把阈值从总体覆盖率细化到核心包/核心类，避免核心功能覆盖率被辅助模块的高覆盖率掩盖。

### 2. Surefire 日志中存在 JaCoCo 插桩警告

运行过程中出现大量类似信息：

```text
Error while instrumenting ... with JaCoCo 0.8.12
Unsupported class file major version 69
```

这类警告主要出现在 JDK 内部类、Mockito/ByteBuddy 动态生成类插桩时。虽然本次真正导致失败的是断言失败，但这些插桩警告会严重污染日志，后续建议：

1. 固定测试运行 JDK 为 17。
2. 减少不必要的 `byte-buddy-agent` 手动挂载。
3. 优先使用动态代理或手写 fake 替代 Mockito 深度 mock。
4. 必要时通过 JaCoCo excludes 排除动态生成类。
