# 规格文档体系

> 一句话定位：本目录为 **SDD（规格驱动开发）唯一事实源**——所有新功能、行为变更，**先在这里写清楚"应该建什么"，再到 `docs/` 确定"怎么建"，最后写代码**。直接写代码不碰规格 = 不合规。
> 阅读前置：无（新人第一份文档）。写或改任何 spec 前，务必先读 [`./common/authoring-conventions.md`](./common/authoring-conventions.md)。

---

## 1. 心智模型：规格是唯一事实源

- **先有规格，后有代码。** 代码不得偏离规格；要改方向，**先改规格再写代码**。
- 每个代码模块都要能追溯到一条规格条目和对应的设计文档。
- 决策变化 → 先改规格再改代码；范围增减 → 反映到 README 路线表。

---

## 2. 目录职责

`specs/` 存放**待做事项与需求分析**，是项目的起点：

| 内容类型 | 说明 |
|---------|------|
| 需求分析 | 功能需求、用户故事、验收标准 |
| 创新点调研 | 技术选型理由、创新方案论证 |
| 任务拆解 | 课程任务的详细说明与实现计划 |
| 技术调研 | 鸿蒙开发、国产数据库等方向调研 |

## 5. 文档写作规范

### 5.1 通用排版（所有 spec 文档遵守）

- **语言**：中文。**格式**：Markdown。
- **每篇顶部三件套**：`> 一句话定位`、`> 阅读前置`（相对链接）、必要时 `> 状态`。
- **表格 + Mermaid 优先**：能用表/图说清的，不写大段话。
- **相对链接**：跨文档引用一律相对路径（如 `../docs/architecture/模块接口与协作规范.md`），便于校验无死链。
- **声明边界**：需求文档只写"要做什么"，不写"怎么实现"。
- **用人话，不生造术语**：软件工程里没有的名词不要造；首次出现的领域术语进术语表。
- **不复制旧文档原文**：吸收参考资料时重写为权威表述，可脚注出处。

### 5.2 EARS 需求句式（`项目需求.md` 及各模块需求文档专用）

> 详见 [`./common/authoring-conventions.md`](./common/authoring-conventions.md) 第2节。

需求一律用 EARS（Easy Approach to Requirements Syntax），**编号化、可追溯、可单测**：

| 模式 | 句式 | 用于 |
|------|------|------|
| 普遍 | `系统应 <响应>` | 恒常要求 |
| 事件驱动 | `当 <触发> 时，系统应 <响应>` | 某输入/事件发生时 |
| 状态驱动 | `在 <状态> 期间，系统应 <响应>` | 处于某状态期间 |
| 非期望 | `如果 <条件>，则系统应 <响应>` | 异常/边界处理 |
| 可选特性 | `若 <特性存在>，系统应 <响应>` | 条件性能力 |

**规则**：
- 每条需求有**唯一编号**（`R<组>.<序>`，如 `R1.2`），按能力分组。
- 一条需求只说一件可验证的事；含糊词（"高效""合理""友好"）要换成可检验条件。
- 正向需求写完，明确写否定需求（`系统不应 …`）标出越权红线。

### 5.3 需求文档基本格式

每份需求/规格文档至少包含：

1. **背景** — 为什么需要这个功能（让没上下文的人也看懂动机）
2. **目标** — 要达到什么效果（明确的、可检验的）
3. **功能描述** — 用 EARS 句式写具体做什么
4. **验收标准** — 怎样算"做完了"（可客观检验的条件列表）
5. **技术约束** — 平台、框架、兼容性等限制
6. **不做（明确排除）** — 防止范围蔓延

### 5.4 文件命名

- 用中文描述性命名，一眼看出内容：`创新点-数据库.md`、`详细设计说明书.md`
- 同一主题多个文件用数字前缀：`01-需求分析.md`、`02-设计方案.md`

## 6. 诚实纪律（写进文档的硬要求）

> 详见 [`./common/authoring-conventions.md`](./common/authoring-conventions.md) 第6节。

- **不说"很好""高效""合理"** 这种无法检验的词。换成可度量的标准（如"正确率≥90%"）。
- **承认不确定性**：暂时确定不了的技术决策，明确标 `[待定]`，不假装已确定。
- **写边界，不写实现**：specs 只写"要什么"，不规定"用什么框架/算法实现"。
- **引用权威来源**：参考外部文档时给链接或脚注，不转述可能过时的内容。

## 7. 开发流程（门控规则）

```text
  specs/              docs/               代码目录
  ───────→           ───────→            ───────→
  需求分析            方案设计             代码实现
  "应该建什么"        "怎么建"            "实际建了什么"
```

> **规则**：需求 → 规格 → 设计方案 → 代码。顺序不可颠倒。一阶段未通过验收，不进入下一阶段。

**门控检查点**：

| 阶段 | 进入条件 | 产出物 |
|------|---------|--------|
| specs | — | 需求文档（含EARS编号） |
| docs | 需求文档通过人审 | 架构设计、API定义、数据模型、实施计划 |
| 代码 | 设计方案通过人审 | 可运行代码 + 测试 |

## 8. 新增一篇 spec 的清单

写或改任何 spec 文档前，先读 [`./common/authoring-conventions.md`](./common/authoring-conventions.md)，然后确认：

- [ ] 顶部"一句话定位 + 阅读前置"齐全
- [ ] 需求用了 EARS 句式并编号（`R<组>.<序>`）
- [ ] 有"不做（明确排除）"小节
- [ ] 跨文档用相对链接（不硬编码绝对路径）
- [ ] 诚实表述：不虚报、不假装确定、不确定项标 `[待定]`
- [ ] 更新本 README 路线表（如有新增/完成文档）
