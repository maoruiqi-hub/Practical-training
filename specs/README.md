# 规格文档体系

> 本目录为 **SDD（规格驱动开发）唯一事实源**——所有新功能、行为变更，**先在这里写清楚"应该建什么"，再到 `docs/` 确定"怎么建"，最后写代码**。直接写代码不碰规格 = 不合规。

## 目录职责

`specs/` 存放**待做事项与需求分析**，是项目的起点：

| 内容类型 | 说明 |
|---------|------|
| 需求分析 | 功能需求、用户故事、验收标准 |
| 创新点调研 | 技术选型理由、创新方案论证 |
| 任务拆解 | 课程任务的详细说明与实现计划 |
| 技术调研 | 鸿蒙开发、国产数据库等方向调研 |

## 规格 → 设计 → 实现 映射

| 规格（specs/） | 设计方案（docs/） | 代码实现 |
|---------------|------------------|---------|
| 需求分析文档 | 架构设计、API 定义 | `frontend/`、`backend/`、`agentic/` |
| 创新点调研 | 技术选型论证 | 对应代码模块 |
| 任务拆解 | 里程碑实现计划 | 各阶段的代码提交 |

## 写作规范

### 需求文档基本格式

每份需求/规格文档至少包含：

1. **背景** — 为什么需要这个功能
2. **目标** — 要达到什么效果
3. **功能描述** — 具体做什么（可用 EARS 格式：当 <条件> 时，系统应 <行为>）
4. **验收标准** — 怎样算"做完了"
5. **技术约束** — 平台、框架、兼容性等限制

### 文件命名

- 用中文描述性命名，一眼看出内容：`创新点-数据库.md`、`详细设计说明书.md`
- 同一主题多个文件用数字前缀：`01-需求分析.md`、`02-设计方案.md`

## 开发流程（门控规则）

```text
  specs/              docs/               代码目录
  ───────→           ───────→            ───────→
  需求分析            方案设计             代码实现
  "应该建什么"        "怎么建"            "实际建了什么"
```

> **规则**：需求 → 规格 → 设计方案 → 代码。顺序不可颠倒。每个代码模块都要能追溯到一条规格条目和对应的设计文档。
