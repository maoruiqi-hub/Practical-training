## 一、业务模块 → 爬塔概念映射

> 本计划的核心理念：**五个模块各自负责业务逻辑，爬塔是前端封装层**。前端不做独立的游戏状态机，所有判定走后端。

| 模块 | 核心实体 | → 爬塔概念 | 数据流向 |
|------|---------|-----------|---------|
| **模块1** 课程内容 | `KnowledgePoint`, `KnowledgeRelation` | 楼层、前置路线 | 塔地图拓扑结构源 |
| **模块1** 课程内容 | `CourseResource` | 补给物品（复习讲义/代码示例等） | 补给弹窗关联的资源 |
| **模块2** 学习任务 | `Task`, `Submission`, `BehaviorLog` | 房间任务、挑战记录、补给/提示行为日志 | 战斗房 = 一个 quiz Task |
| **模块3** 测评评价 | `Question`, `SubmissionAnswer`, `Exam` | 战斗题、Boss 战、判分结果 | 答题提交 → 后端判分 → **后端自动发游戏事件** |
| **模块3** 测评评价 | `KnowledgeMastery` | 掌握度 | 诊断结果源 |
| **模块4** 学生画像 | `StudentProfile` | HUD（HP/ATK/DEF/EXP/金币/等级） | 属性面板数据源，**唯读** |
| **模块4** 学生画像 | `GameEvent` 事件监听 | 游戏引擎 | **唯一的游戏状态更新入口** |
| **模块4** 学生画像 | `KnowledgePointFloorStatus` | 楼层四色状态 | 塔地图 UI 的判定源 |
| **模块5** 学情分析 | `RiskAlert` | HP 危险、卡顿预警 | 学生端提示、教师端预警 |

**原则**：前端只读数据 + 调已有 API，不自己做 HP/判决/解锁。答题判分后**后端已自动发游戏事件**，前端不应再重复发 `answer_correct`/`answer_wrong`。

#### 任务 A2：塔地图数据源切换（0.5天）

**文件**：`profile/service/impl/ProfileServiceImpl.java`

**当前实现**（[第542行](backend/src/main/java/com/neu/CoursePlatform/profile/service/impl/ProfileServiceImpl.java#L542)）：`getTowerMap()` 用 `CompetencyScore + AbilityPoint` 生成楼层，第604行 `getCourseAbilityMap()` 从 `AbilityPoint` 查。

**目标实现**：改为四表联合查询：

```
KnowledgePoint          → 楼层名称、描述、所属区域（chapter）
KnowledgeRelation       → 前置依赖 DAG（判定楼层是否锁定）
KnowledgeMastery        → 掌握度分数（判定 cleared/weak/available）
KnowledgePointFloorStatus → 楼层通关状态（cleared 标记）
```

**关键逻辑**：

## 六、失败条件（红线）

以下任一发生 = 本计划失败：

1. ❌ 塔地图只是换皮菜单，点击楼层后仍然是传统刷题流程
2. ❌ 诊断后没有真正跳过已掌握内容，所有学生走同样路线
3. ❌ 补给随机弹出，与错因/HP 状态无关
4. ❌ 答题后属性面板不更新（游戏事件链路未打通）
5. ❌ 答题后属性面板重复更新（HP/EXP 双倍计算——说明前端和后端重复发了游戏事件）
6. ❌ 页面刷新后塔地图状态丢失（没有持久化到后端）
7. ❌ agentic 不可用时前端白屏或报错
