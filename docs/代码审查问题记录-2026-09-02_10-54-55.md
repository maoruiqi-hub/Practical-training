### 方案一：关闭画像和成长数据的伪造入口

对应问题：`BLOCKER-01`

#### 后端改造

1. 删除或仅在 `dev` Profile 下注册 `ProfileController` 中的模拟答题接口。
2. 删除公开的 `/api/profile/event/receive` 和 `/api/profile/string/**/growth` 写接口，模块间更新统一改为 Spring `ApplicationEventPublisher` 进程内事件。
3. 如果未来确实拆分成独立服务，再增加单独的内部 API：
   - 使用服务账号或签名鉴权，不复用学生 Session。
   - 请求必须包含 `eventId`、事件类型、来源模块、学生、课程、发生时间和业务来源 ID。
   - 数据库对 `eventId` 建唯一索引，重复事件直接返回已有结果。
4. 学生侧 `/api/students/{studentId}/growth/add`、徽章授予、能力强制更新等写接口不得允许学生自行调用；只允许可信服务事件或有课程权限的管理员操作。
5. 成长值由事件类型映射表计算，客户端不能直接提交任意 `amount`。例如楼层通关固定加 80，Boss 通关固定加 250。

#### 前端配合

- 删除对模拟答题、直接增加成长值和手动刷新能力写接口的调用。
- 学生页面只读取画像，不直接构造成长变化。

#### 必须补充的测试

- 未登录、学生本人、其他学生、普通教师调用上述写接口均被拒绝。
- 合法领域事件只生效一次；重复 `eventId` 不重复加分。
- 客户端伪造 `amount` 不影响实际成长值。

#### 验收标准

- 通过公开 HTTP API 无法直接改变学生成长值、能力分和徽章。
- 所有画像变化都能追踪到唯一可信业务事件。

### 方案二：重建服务端可信的爬塔正确率计算

对应问题：`BLOCKER-02`

#### 后端改造

1. `completeNode` 和 `diagnoseNode` 强制要求 `packId`，缺失直接返回业务错误。
2. 加载题包后严格验证学生、课程、运行、节点、模式和题包有效期。
3. 服务端以题包中的题目编号作为唯一标准集合，不使用客户端提交列表决定分母。
4. 将客户端答案转换成 `Map<questionId, answer>`：
   - 重复题号直接拒绝，不允许后一个覆盖前一个。
   - 题包之外的题号直接拒绝。
   - 题包内缺失的客观题按未答/错误计入分母。
5. 正确率公式固定为：`正确的客观题数量 / 题包中全部客观题数量`。
6. 主观题不进入自动正确率；如果题包没有任何客观题，则不能走自动战斗结算，应进入教师评阅或更换题包。
7. 服务端忽略客户端传入的 `correct`、`autoGradable`、`correctRate` 和 `cleared`，全部根据数据库题目和学生答案重新计算。

#### 前端配合

- 战斗和诊断提交必须携带服务端返回的 `packId`。
- 前端正确率仅用于即时动画；最终展示以服务器返回的 `correctRate` 为准。
- 服务器拒绝结算时保留当前答题状态并显示具体原因。

#### 必须补充的测试

- 缺少、伪造、过期和其他学生的题包均被拒绝。
- 只答一道正确题时，其他未答题计为错误。
- 重复正确题、题包外题目、伪造 `correct=true` 不得提高正确率。
- 同一个 `evaluationId` 重复提交不会重复更新掌握度或奖励。

#### 验收标准

- 任意修改客户端请求都不能改变服务器依据题包计算的正确率。
- 通关、奖励、能力变化与服务器正确率保持一致。

### 方案三：按任务标准答卷进行测验自动评分

对应问题：`BLOCKER-03`

#### 后端改造

1. 提交测验时由服务端查询 `task_question` 关系，获取当前任务的完整标准题目集合。
2. 将学生答案按题号去重；重复题号、任务外题号直接拒绝。
3. 对任务内缺失答案保留空答案记录，客观题计 0 分，主观题进入待评阅状态。
4. 自动得分只遍历任务标准题目，不遍历客户端答案列表。
5. 自动得分限制在任务满分内；若题目分值合计与任务满分不一致，任务发布时阻止发布并提示教师修正。
6. 保存 `SubmissionAnswer` 时，每次提交和每道题只允许一条记录，数据库增加唯一约束 `(submission_id, question_id)`。
7. 统一使用 `QuestionAnswerEvaluator`，删除 `TaskSubmissionServiceImpl` 内重复的答案匹配实现。

#### 前端配合

- 提交前提示未答题，但不把前端完整性校验当作安全边界。
- 服务端返回重复题、题目已变更等错误时，刷新题目并提示重新确认。

#### 必须补充的测试

- 重复题、其他任务题、其他课程题、缺题和不存在题目。
- 单选、多选、填空的规范化匹配。
- 题目分值总和超过任务满分时不能获得超分。
- 主客观混合任务只自动结算客观题，最终总分与分题得分一致。

#### 验收标准

- 自动评分结果仅由任务题目、数据库标准答案和学生答案决定。
- 无法通过构造请求获得任务满分以上的成绩。

### 方案四：完成密码哈希迁移和敏感字段隔离

对应问题：`BLOCKER-04`

#### 后端改造

1. 引入 Spring Security Crypto，仅使用 `PasswordEncoder`（建议 BCrypt），不必在本阶段整体引入 Spring Security 登录框架。
2. 注册、批量导入和管理员创建账号时统一调用 `passwordEncoder.encode()`。
3. 登录改为 `passwordEncoder.matches(raw, encoded)`。
4. 对现有数据库执行一次密码迁移：
   - 如果当前密码是明文，可在受控迁移脚本中逐条哈希后覆盖。
   - 迁移完成后禁止再次写入明文。
5. `Student`、`Teacher` 实体的密码字段增加 `@JsonProperty(access = WRITE_ONLY)`；所有查询接口进一步改为 DTO，不直接返回持久化实体。
6. 管理员更新用户时，空密码表示不修改；非空密码必须重新哈希。
7. Session 中不保存带密码字段的完整实体，改存精简登录主体，例如用户 ID、角色和姓名。

#### 必须补充的测试

- 数据库中不存在新写入的明文密码。
- 登录响应、学生列表、教师搜索和错误日志均不包含密码。
- 旧账号迁移后仍可登录；错误密码不能登录。

#### 验收标准

- API、日志和 Session 不暴露密码。
- 数据库泄露时不能直接得到用户原始密码。

### 方案五：将重新提交改为原子事务

#### 后端改造

1. 控制器只负责参数接收，把完整提交流程下沉到 `TaskSubmissionService` 的事务方法。

4. 文件系统不受数据库事务控制：
   - 先保存到临时路径。
   - 数据库事务成功后移动到正式路径。
   - 事务失败时删除临时文件。
5. 旧提交只覆盖“当前有效提交”，不得再次修改历史 `superseded` 记录。

#### 必须补充的测试

- 文件格式错误、内容为空、文件保存失败、答案保存失败时旧提交保持有效。
- 成功重新提交后只有最新一条为有效状态。
- 并发提交不会突破最大次数或产生两条有效提交。

#### 验收标准

- 任意失败路径都不会损坏已有有效提交。
- 提交次数和有效提交状态在并发情况下保持一致。

### 方案六：建立统一且可验证的成绩规则

#### 验收标准

### 方案九：为动态校准建立安全发布门槛

对应问题：`BLOCKER-09`

#### 校准规则

第一版建议采用保守规则，避免少量数据驱动大幅调整：

1. 共同样本少于 10：不调整，候选权重完全沿用正式版本，报告标记“样本不足”。
2. 训练样本达到 10 但验证样本少于 3：允许生成观察报告，不允许发布自动调整结果。
3. 验证相关方向与训练集冲突：该关系不调整，并标记“验证冲突”。
4. 相关度不为正或置信度低于门槛：保持原权重，不使用固定 `0.05` 人造权重。
5. 单次权重变化设置上限，例如不超过原权重的 ±20%，防止矩阵突变。
6. 每一行调整后精确归一化为 1，最后一个相关能力吸收小数残差。
7. 教师定义的“不相关”和“不确定”永远不由算法自动改成“相关”。

#### 版本与发布

1. 候选版本保存完整报告、创建人、创建时间、基线版本、样本时间范围和算法版本。
2. 发布时必须确认候选 `based_on_version` 等于当前正式版本，否则候选过期，要求重新校准。
3. 发布接口在同一事务中归档旧版本并发布新版本。
4. 数据库保证每门课程最多一个 `published` 版本。
5. 发布前检查：
   - 没有跨课程或孤儿关系。
   - 每个假能力点的相关权重和为 1。
   - 所有数值在合法范围内。
   - 没有验证冲突的自动调整项。
6. 样本不足时仍可保存“报告”，但没有实际变化的候选无需发布。

#### 前端配合

- 候选版本和报告从后端加载，刷新页面后仍可查看。
- 发布按钮只在后端返回 `publishable=true` 时启用。
- 教师看到的是“样本不足、方向一致、方向冲突、变化幅度、当前/候选权重”等抽象信息，不直接编辑算法参数。
- 发布前展示变更摘要并要求教师确认。

#### 必须补充的测试

- 0、2、9、10、20 个共同样本的边界情况。
- 负相关、训练/验证方向冲突、常量数据和异常值。
- 候选生成后正式版本变化，旧候选不能发布。
- 并发发布后每课程仍只有一个正式版本。
- 归一化后每行权重精确满足约束。

#### 验收标准

- 没有足够且方向一致的数据时，正式矩阵不会变化。
- 每一次正式矩阵变化都能解释其证据、基线和教师确认记录。
