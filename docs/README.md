# 实现文档

> 本目录存放**确定后的设计方案与实现说明**——代码写完了，这里记录"实际建了什么"。

## 目录职责

`docs/` 存放**已确定的技术方案与实现文档**，是项目的沉淀层：

| 内容类型 | 说明 |
|---------|------|
| 设计说明 | 架构设计、数据模型、接口定义 |
| API 文档 | 后端接口规格与使用说明 |
| 部署文档 | 环境搭建、部署流程、运维指南 |
| 实现总结 | 阶段性开发总结与技术复盘 |

## 目录结构

```
docs/
├── README.md               本文件 — 文档目录说明
├── architecture/           架构设计文档
├── api/                    API 文档
├── deployment/             部署与运维文档
└── summaries/              开发总结与复盘
```

## 与 specs/ 的区别

| | `specs/` | `docs/` |
|---|---------|---------|
| **定位** | 待做与需求 | 确定后的实现 |
| **时机** | 开发前 | 开发后 |
| **内容** | 需求分析、创新点、任务拆解 | 设计方案、API 文档、部署说明 |
| **可变性** | 需求可能调整 | 反映最终落地结果 |
| **读者** | 开发者（知道要建什么） | 维护者 / 新人（知道建了什么） |

## 写作规范

### 设计文档基本格式

每份设计文档至少包含：

1. **背景** — 回顾对应的需求（可链接到 `specs/` 中的文档）
2. **方案概述** — 一两句话讲清楚整体方案
3. **架构 / 流程** — 用图或文字描述系统结构
4. **接口定义** — 关键 API 或模块间接口
5. **关键决策** — 为什么选这个方案而不是别的
6. **已知限制** — 当前方案的边界与不足

### 文件命名

- 按主题分类建子目录：`architecture/`、`api/`、`deployment/`
- 文件名用中文描述：`数据库设计.md`、`知识图谱服务架构.md`

> **规则**：文档反映的是**当前代码的真实状态**，代码改了文档要跟着改。
