# 设计文档

> 本目录存放**确定后的技术方案与设计文档**——需求明确后、写代码前，在这里确定"怎么建"。

## 目录职责

`docs/` 是规格（`specs/`）与代码之间的桥梁，存放**已确定的技术方案**：

| 内容类型 | 说明 |
|---------|------|
| 架构设计 | 系统分层、模块划分、技术选型理由 |
| 数据模型 | ER 图、表结构、字段说明 |
| API 定义 | 接口路径、请求/响应格式、鉴权方案 |
| 部署方案 | 环境规划、CI/CD 流程、容器化方案 |
| 实现计划 | 分阶段任务拆解（如 10/20/30/40 等里程碑文档） |

## 目录结构

```
docs/
├── README.md                    本文件 — 文档目录说明
├── architecture/                架构设计文档（系统分层、模块关系）
│   └── 模块接口与协作规范.md       ★ 5 模块接口契约与协作开发指南
├── data-model/                  数据模型与数据库设计
├── api/                         API 接口定义
├── deployment/                  部署与运维方案
└── plans/                       实施计划（每个模块一份 .plan.md）
    ├── plan-writing-guide.md    ★ 实施计划写作规范（写 plan 前必读）
    └── _TEMPLATE.md             计划模板（复制此文件新增 plan）
```

## 与 specs/ 的区别

| | `specs/` | `docs/` |
|---|---------|---------|
| **定位** | 应该建什么 | 怎么建 |
| **时机** | 需求分析阶段 | 方案设计阶段（写代码前） |
| **内容** | 需求分析、创新点、任务要求 | 架构设计、API 定义、数据模型 |
| **问题** | "用户要什么？" | "技术上怎么实现？" |
| **读者** | PM / 全团队 | 开发者（照着设计写代码） |

## 开发流程中的位置

```text
  specs/              docs/              代码目录
  ───────→           ───────→            ───────→
  需求分析            方案设计             代码实现
  "应该建什么"        "怎么建"            "实际建了什么"
```

> **规则**：先 specs 明确需求 → 再 docs 确定方案 → 最后写代码。顺序不可颠倒。

## 写作规范

### 设计文档基本格式

每份设计文档至少包含：

1. **需求回顾** — 链接到 `specs/` 中对应的需求文档
2. **方案概述** — 一两句话讲清楚整体技术方案
3. **架构 / 流程** — 用 ASCII 图或文字描述系统结构、数据流
4. **接口定义** — 关键 API 或模块间接口的具体定义
5. **关键决策** — 为什么选这个方案而不是别的（技术选型理由）
6. **实现计划** — 分哪些步骤、预估工作量

### 文件命名

- 按主题分类建子目录：`architecture/`、`data-model/`、`api/`、`plans/`
- 实施计划命名：`module<n>-<中文名>.plan.md`，如 `module1-课程内容与知识组织.plan.md`
- 文件名用中文描述：`数据库设计.md`、`知识图谱服务架构.md`

> **计划文档（plans/）有独立的写作规范**，见 [`plans/plan-writing-guide.md`](plans/plan-writing-guide.md)，写 plan 前必读。
