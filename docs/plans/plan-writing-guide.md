# 实施计划写作规范（如何写 plan）

> 一句话定位：规定 `docs/plans/` 里**实施计划文档**怎么写——把 `specs/` 的规格拆成小而可验证、按依赖排序、带验收与验证的任务，经人审后再进入实现。写或改任何 plan 前，先读本篇。
> 阅读前置：[`../../specs/README.md`](../../specs/README.md)、[`../../specs/common/authoring-conventions.md`](../../specs/common/authoring-conventions.md)、[`../architecture/模块接口与协作规范.md`](../architecture/模块接口与协作规范.md)

---

## 0. 定位：规格 → 计划 → 实现 三联

```
specs/              docs/plans/              代码目录
「应该建什么」  ──→   「怎么分步建」    ──→   「实际建了什么」
 (需求/规格)          (本目录：实施计划)        (代码实现)
```

- **plan 是 spec 与代码之间的中间物**：回引规格需求编号，产出可执行任务清单与验收门。
- plan 讲"怎么分步建 + 验收"，不讲"为什么需要"（那是 specs 的事）。

---

## 1. 何时写 plan / 何时不写

**写**（满足任一）：
- 要实现某个模块的功能（5个模块各需一份 plan）
- 改动跨多个模块 / 涉及架构决策
- 需要与团队其他人协作，约定接口时序

**不写**（直接做）：
- 单文件、范围明确的小修；typo；注释补充
- 需求自洽无歧义的微型改动（改一个 API 返回字段等）

---

## 2. 门控生命周期（四阶段，逐阶段人审）

沿用 SDD 的 gated workflow——**当前阶段未通过验收，不进入下一阶段**：

```
SPECIFY ──→ PLAN ──→ TASKS ──→ IMPLEMENT
(规格已在      (本目录     (任务清单     (按任务实现，
 specs/)        产出)       +检查点)      每检查点回审)
   └─人审───────┴─人审──────┴─人审─────────┴─人审
```

- **先读后写**：进入 PLAN 先只读——读对应 spec、读 `docs/architecture/` 看接口契约、读相关代码（如有）。
- **先亮假设**：动笔前列出你做的假设（技术栈/边界/取舍），让人先纠正，别静默填空。
- **规划阶段不写代码**，只写计划。

---

## 3. 五条核心原则

1. **依赖图自底向上**：先画"谁依赖谁"（参考[模块接口文档](../architecture/模块接口与协作规范.md)的依赖关系），实现顺序按依赖，先建地基。
2. **垂直切片，不要水平分层**：一条任务交付**一条完整可跑通的路径**，而不是"先建所有表、再建所有 API"。
   - ✅ 好：`T1 教师能创建课程（schema + API 一条龙）`
   - ❌ 坏：`T1 建全部表 / T2 建全部 API / T3 建全部 UI`
3. **原子任务**：单任务 ≤ ~5 文件、可在一个专注 session 内做完、验收 ≤3 条。标题里出现"和/与"通常意味着该拆成两条。
4. **每条任务都有验收标准 + 验证命令**：没有可执行验证步骤的任务不算合格任务。
5. **阶段间设检查点**：每 2–3 个任务后留一个 checkpoint（测试通过 / 可启动 / 核心路径跑通 / 人审），让系统始终处于可工作状态；高风险任务排前面（fail fast）。

---

## 4. 任务定级表（超过 L 必须再拆）

| 级别 | 文件数 | 范围 | 例 |
|------|--------|------|-----|
| XS | 1 | 单函数/配置 | 加一条校验规则 |
| S | 1–2 | 单组件/单端点 | 新增一个 API 端点 |
| M | 3–5 | 一条特性切片 | 知识点 CRUD + 测试 |
| L | 5–8 | 多组件特性 | 知识图谱构建 + 可视化 + 关系管理 |
| XL | 8+ | **太大，必须再拆** | — |

**需要再拆的信号**：
- 预估 > 2 小时工作量
- 验收说不清（> 3 条）
- 跨两个独立子系统
- 标题里有"和"

## 5. plan 文档结构（强制模板）

每份 plan 复制 [`_TEMPLATE.md`](./_TEMPLATE.md)，含以下小节：

| 小节 | 内容 |
|------|------|
| 顶部三件套 | `> 一句话定位`、`> 阅读前置`、`> 状态` |
| **Context（背景）** | 为什么做、解决什么问题、预期结果 |
| **Goals（目标）** | 明确的、可检验的目标列表 |
| **Non-Goals（不做）** | 明确不做什么，防范围蔓延 |
| **回引规格** | 对应 `specs/` 的需求文档与 R 编号 |
| **架构决策** | 关键决策 + 一句理由（如有） |
| **备选方案** | 考虑过的其它方案 + 为何不选（如有） |
| **假设** | 动笔前亮出的假设，请人先纠正 |
| **任务清单（分阶段 + 检查点）** | 见 §6 任务格式；按依赖排序 |
| **风险与缓解** | 表格：风险 / 影响 / 缓解 |
| **Open Questions** | 需人拍板的开放问题 |
| **越权红线** | 本 plan 明确不做的事 |
| **完成定义（DoD）** | 整体怎么证明做完了 |
| **端到端验证** | 可执行的验证命令/步骤 |

---

## 6. 任务格式（强制回引需求）

```markdown
- [ ] **T<n> — <动词短语>**（满足 R<…>, R<…>）
  - 验收：<完成时必须为真的可检条件，≤3 条>
  - 验证：<可执行命令，如 pytest -k xxx / npm test -- --grep>
  - 依赖：<前置任务号，或"无">
  - 文件：<将改动的目录/文件，≤~5>
  - 规模：XS / S / M / L
```

检查点格式：
```markdown
### 🔍 检查点：阶段 X 完成
- [ ] 全部测试通过
- [ ] 可构建/可启动
- [ ] 核心路径端到端跑通
- [ ] 人审通过再继续
```

规则：
- **每条回引 spec 需求编号**（保证 spec ↔ plan ↔ 代码可追溯）。
- 任务按**依赖顺序**排，不按重要性。
- 高风险任务靠前（fail fast）。
- 阶段间设检查点；末尾给该 plan 的 DoD。

## 7. 各模块 Plan 示例结构

以模块1（课程内容与知识组织）为例，一份 plan 的任务阶段参考：

```
阶段1：地基
  T1  课程 CRUD（R1.1–R1.3）
  T2  知识点 CRUD（R2.1–R2.2）
  T3  知识点关系管理（R2.3）
  🔍 检查点 1

阶段2：核心
  T4  课程资源上传与管理（R1.4）
  T5  资源在线预览（R1.5）
  T6  知识图谱手动构建与可视化（R2.4）
  T7  知识点详情页（R2.5）
  🔍 检查点 2

阶段3：AI 智能
  T8  知识点自动提取（R2.6 → agentic）
  T9  知识图谱自动构建（R2.7 → agentic）
  T10 PPT 讲解 / 知识点问答（R2.8–R2.9 → agentic）
  T11 能力图谱 + 薄弱知识点统计（R3.1–R3.2）
  🔍 检查点 3

阶段4：联调
  T12 前端对接 + 集成测试
  T13 Bug 修复 + 文档更新
  🔍 检查点 4 → 完成
```

## 8. 命名与文件组织

- 每个模块一份 plan 文件：`module1-课程内容与知识组织.plan.md`
- 模板文件：[`_TEMPLATE.md`](./_TEMPLATE.md)
- **状态**：顶部 `> 状态：草拟 / 待审 / 已批准 / 实施中 / 已完成`
- 完成后：更新 `docs/plans/README.md` 索引表（待建）状态

---

## 9. 并行化（5 人协作时）

| 可并行 | 必须串行 | 需协调 |
|--------|---------|--------|
| 各模块内部的独立功能 | 共享数据表结构的变更 | 共享同一 API 契约的功能 |
| 独立模块的测试 | agentic 服务接口变更 | 模块间依赖的接口（先定契约再并行） |
| 文档更新 | — | — |

**原则**：参考[模块接口文档](../architecture/模块接口与协作规范.md)的 Phase 划分——同一 Phase 内各模块尽量并行，Phase 之间串行。

---

## 10. 反模式 / Red Flags

| 反模式 | 现实 |
|--------|------|
| "边做边想" | 那是返工的根源；10 分钟规划省几小时 |
| 任务写"实现该功能"无验收 | 等于没写任务 |
| 全是 XL 任务、无检查点 | 不可执行 |
| 不考虑依赖顺序 | 地基没打就盖楼 |
| 把 plan 当 spec 写（堆需求） | 需求在 specs；plan 只讲"怎么分步建 + 验收" |

---

## 11. 新增一份 plan 的清单

- [ ] 复制 `_TEMPLATE.md`，顶部三件套齐全；命名对齐模块名
- [ ] 有 Context / Goals / **Non-Goals** / 假设 / 风险 / Open Questions
- [ ] 回引 `specs/` 的需求编号（R…）
- [ ] 任务垂直切片、按依赖排序、每条 ≤5 文件、带验收+验证+规模
- [ ] 阶段间有检查点；高风险任务靠前
- [ ] 诚实表述；写明越权红线
- [ ] 末尾有 DoD 与端到端验证
