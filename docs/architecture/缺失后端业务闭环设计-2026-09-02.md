- 记录时间：2026-09-02
- 适用分支：`codex/ability-point-mapping`
- 状态：阶段 A、B、首批徽章及管理端来源审计闭环已完成（2026-09-04 09:21）
- 目标：删除通用假事件接口后，为仍然需要的答题画像、能力投影、补给、奖励、非战斗房间和徽章建立可信后端闭环。

## 1. 当前清理结果

本轮已经完成以下止血工作：

1. 删除前端 `sendGameEvent(studentId, body)`，不再请求已经关闭的 `/api/students/{studentId}/game-event`。
2. 删除战斗页面逐题上报 `answer_correct`、`answer_wrong`、`answer_skipped` 的逻辑。正确性只能由最终提交后的服务端判分产生。
3. 删除 AI 导师通过游戏事件上报调用次数的逻辑。AI 使用记录以后只能作为学习行为日志，不能直接改变画像。
4. 移除补给弹窗及其伪结算调用。
5. 移除前端本地奖励属性增量，以及向后端提交任意 `hp_delta`、`exp_delta`、`coin_delta` 的逻辑。
6. 地图上的宝箱、休息、商店和随机事件房间暂时不可进入，并明确显示“后端能力待实现”，不再假装结算成功。
7. `POST /api/learning-logs` 只记录行为，不再根据前端提供的行为类型触发补给、提示和画像属性变化。

目前仍然可用的真实链路：

- 普通任务提交、任务标准题集评分和答案明细。
- 爬塔诊断、战斗、精英和 Boss 的题包校验、服务端判分与节点结算。
- 答题证据、知识掌握度和能力雷达中的知识证据部分。

## 2. 删除假接口后暴露的能力缺口

| 缺口 | 当前情况 | 需要补充的真实后端能力 |
|---|---|---|
| 答题到画像 | 服务端有答题证据，但旧画像仍依赖通用游戏事件 | 从已落库答题证据投影 HP、ATK、经验和连续正确数 |
| 课程要点分 | `competency_score` 初始固定为 50，旧规则为答对 +2、答错 -1 | 从 `knowledge_mastery` 和知识点关系聚合，不再使用人为增减 |
| 真能力分 | 矩阵输入可能仍是旧 `competency_score` | 使用可信课程要点向量乘正式映射矩阵 |
| 徽章 | 授予服务没有可信调用者，旧方法接受外部统计值 | 徽章规则自行查询答题、任务、爬塔和反馈事实 |
| 补给 | 没有库存、持有数量和消费记录 | 增加运行内库存、消费命令和幂等日志 |
| 提示 | 前端可把行为日志伪装为使用提示 | 校验题包、题目、提示次数和消耗后返回提示 |
| 奖励 | 奖励选项和属性增量由前端生成 | 服务端生成并保存奖励选项，只接受 `optionId` |
| 非战斗房间 | 共用战斗结算接口，但没有题包和房间规则 | 增加独立的房间解决命令，不使用正确率字段 |
| AI 使用统计 | 以前通过游戏事件上报 | 作为纯行为日志，由 Session 绑定用户，不修改画像 |
| 幂等和审计 | 内部 `GameEvent.eventId` 没有统一消费账本 | 增加投影账本和业务动作唯一键 |

## 3. 总体设计原则

### 3.1 前端提交命令，不提交结果

前端只能表达：

- 我提交了哪些答案。
- 我想使用哪个库存物品。
- 我选择了哪个后端提供的奖励选项。
- 我选择了非战斗房间中的哪个合法动作。

前端不得提交：

- `correct`、`correctRate` 作为最终判定依据。
- `eventType` 让后端直接执行任意事件。
- `hpDelta`、`expDelta`、`coinDelta` 等属性变化。
- 总正确数、连续正确数等徽章统计结果。

### 3.2 先产生可信事实，再更新投影视图

统一处理链路：

```text
业务命令
  → 校验 Session、课程、运行、节点和对象归属
  → 写入可信业务事实
  → 写入幂等账本
  → 在同一事务中更新画像、能力或库存投影
  → 返回服务端结果
```

第一版保持单体事务，不引入消息队列。未来拆分服务时再把可信事实接入 Outbox。

### 3.3 AI 不参与数值结算

AI 可以生成诊断文字、解释和学习建议，但不能决定：

- 答案是否正确。
- 成长值和奖励数值。
- 徽章是否授予。
- 能力矩阵权重是否自动发布。

## 4. 答题证据到画像的真实链路

### 4.1 可信来源

- 普通测验：`submission_answer` 和 `learning_answer_evidence`。
- 爬塔答题：服务端校验题包后写入的 `learning_answer_evidence`。
- 节点结果：`student_tower_attempt`。

### 4.2 投影服务

新增 `ProfileProjectionService`，只接受已落库记录的 ID，例如：

```java
applyAnswerEvidence(String evidenceId);
applyTowerAttempt(String attemptId);
applyInventoryAction(String actionId);
```

服务必须重新读取数据库事实，不能信任调用参数中的正确性和数值。

建议新增表：

```text
profile_projection_ledger
- id
- student_no
- course_code
- source_type
- source_id
- projection_type
- applied_at
- UNIQUE(source_type, source_id, projection_type)
```

同一答题证据或节点尝试重复提交时，画像只能变化一次。

### 4.3 第一版成长规则

规则由后端固定配置管理，并带版本号：

- 客观题答对：更新连续正确、最近答题窗口和 ATK。
- 客观题答错或未答：连续正确归零，更新最近答题窗口。
- 单题成长值只按已落库的答题证据走普通答题档位；任务、节点和 Boss 的高额奖励只按服务端确认的完成事实结算，不按前端逐题事件结算。
- 节点失败、普通通关、精英通关和 Boss 通关使用固定奖励策略。
- 所有属性限制在后端定义的合法范围内。

### 4.4 已实现结果（2026-09-02）

- `LearningEvidenceService` 只有在答题证据首次成功落库后，才按证据 ID 调用 `ProfileProjectionService`。
- 投影服务按 ID 重新读取 `learning_answer_evidence`，不接受客户端提供的正确性或属性增量。
- `profile_projection_ledger` 以“事实类型 + 事实 ID + 投影类型”唯一约束保证同一证据只更新一次。
- HP、ATK、连续正确、最近答题窗口、学习状态继续复用原 `ProfileServiceImpl`；经验、金币和等级继续复用原 `GrowthRuleEngine`。
- 单题证据统一使用原普通答题档位（答对 10 经验、20 金币），不会因题目来自测验或 Boss 房间而误用“整场测验/Boss 完成”的高档奖励；节点完成奖励仍由已有节点事件结算。
- 旧 `ANSWER_CORRECT/ANSWER_WRONG/ANSWER_SKIPPED` 画像监听已停止，避免同一答题同时通过事件和证据重复增加属性。
- 证据、掌握度、画像账本和画像更新参加同一事务；徽章评估在该事务提交后触发，徽章失败不会回滚答题。
- 条件插入使用 PostgreSQL、KingbaseES 和 H2 均可执行的 SQL，唯一索引仍是最终完整性防线。

当前限制：旧画像模型的学生编号和课程编号仍为 `Integer`，因此非数字业务编号会跳过画像投影并记录告警。要彻底消除此限制，需要把整个 profile 子域统一迁移为 `String` ID，不能只改本服务的参数类型。

## 5. 两类能力向量的统一数据源

### 5.1 课程要点向量

旧 `competency_score` 不再初始化为固定 50，也不再执行答对 +2、答错 -1。

课程要点 `A_i` 由其关联知识点掌握度聚合：

```text
A_i = Σ(w_ik × mastery_k) / Σ(w_ik)
```

- `mastery_k` 来自 `knowledge_mastery`。
- `w_ik` 来自课程要点与知识点的关系；第一版没有权重时等权。
- 没有任何证据时返回 `null/暂无证据`，不能用 50 冒充掌握度。
- 返回 `evidenceCount`、`coverage` 和 `formulaVersion`。

如未来需要性能缓存，可以继续使用 `competency_score` 表，但必须补充：

- `score_source = knowledge_mastery_projection`
- `formula_version`
- `evidence_count`
- `coverage`
- `last_evidence_at`

当前实现不读取该旧表作为学生能力事实，也不再创建固定 50 分记录；先采用查询时实时投影，避免缓存失效与双数据源问题。

### 5.2 真能力向量

对当前正式矩阵中的 `related` 关系计算：

```text
C_j = Σ(M_ij × A_i) / Σ(M_ij)
```

- `M_ij` 使用正式矩阵版本中的 `strength`。
- `unrelated` 不进入计算。
- `uncertain` 只展示关系，不进入正式学生能力分。
- 同时返回矩阵版本、贡献项、覆盖率和综合置信度。
- 没有足够课程要点证据时显示“证据不足”，不能补默认能力分。

### 5.3 接口调整

- 保留读取：`GET /api/students/{studentId}/ability-radar`。
- 保留读取：`GET /api/profile/{studentNo}/{courseCode}/true-competency`。
- 学生侧删除“强制更新能力分”语义。
- 如需重建缓存，只提供教师或管理员接口：
  `POST /api/courses/{courseCode}/ability-projections/rebuild`。

### 5.4 已实现结果（2026-09-02 19:48）

- 新增统一 `StudentAbilityProjectionService`，课程要点和真能力读取完全相同的学生证据链。
- 课程要点按已产生答题证据的知识点掌握度加权；知识点重要度复用已有 `KnowledgePoint.importance`，没有证据的知识点不以 50 参与分子或分母。
- 一个课程要点完全没有证据时返回 `score: null`、`hasEvidence: false`，并同时返回证据数、知识点总数、覆盖率和公式版本 `knowledge_mastery_weighted_v1`。
- 真能力只使用正式矩阵中的 `related` 且强度大于零的关系；`unrelated` 和 `uncertain` 不进入分数。
- 真能力按当前已有证据的关系强度归一化计算，同时返回已配置关系覆盖率、矩阵版本、综合置信度和逐项贡献。
- 真能力完全没有有效课程要点时仍返回能力定义，但分数为 `null`、状态为 `evidence_insufficient`，不再隐藏维度或伪造分数。
- 画像摘要、两套课程要点接口、课程要点雷达、真能力接口和行为校准输入都已切换到统一投影；旧 `competency_score` 仅保留兼容表，不再初始化或作为事实读取。
- 前端课程要点卡片、知识点标签和两个雷达图均支持“暂无证据”；无证据维度不作为 0 分绘制。

## 6. 补给、提示和库存

### 6.1 数据表

```text
tower_run_inventory
- id
- run_id
- student_no
- item_code
- quantity
- version
- updated_at
- UNIQUE(run_id, item_code)

tower_action_log
- action_id
- run_id
- node_id
- student_no
- action_type
- target_id
- result_json
- created_at
- UNIQUE(action_id)
```

### 6.2 使用补给

```http
POST /api/tower-runs/{runId}/nodes/{nodeId}/inventory/{itemCode}/use
Content-Type: application/json

{
  "actionId": "客户端生成的幂等键"
}
```

后端校验：

1. Session 学生拥有该运行。
2. 节点是当前可操作节点。
3. 物品存在且数量大于零。
4. 物品允许在当前房间使用。
5. `actionId` 未处理；重复请求返回第一次结果。
6. 扣减库存和更新画像处于同一事务。

请求不能携带回血量等数值。

### 6.3 使用提示

```http
POST /api/tower-runs/{runId}/nodes/{nodeId}/questions/{questionId}/hint

{
  "packId": "题包编号",
  "actionId": "幂等键"
}
```

后端确认题目属于题包，并根据课程配置返回教师提示或题目提示。没有真实提示内容时明确返回“未配置”，不能让 AI 临时生成答案并作为正式提示。

## 7. 奖励与非战斗房间

### 7.1 服务端节点选项（实施版）

新增：

```text
tower_node_option
- option_id
- run_id
- node_id
- option_kind       # reward / room
- option_code
- option_snapshot_json
- selected
- created_at
- selected_at
- UNIQUE(run_id, node_id, option_code)
```

实施时将奖励与非战斗房间统一为“节点选项”，避免再建两套生成、选择和幂等逻辑。战斗通关后生成 `reward`选项，宝箱、休息、商店和事件节点生成 `room` 选项。选项快照由服务端固定规则产生，前端只展示后端返回的名称、说明和选项编号。

第一版不让 AI 参与选项生成，规则版本为 `tower_growth_v1`：

- 战斗奖励：金币、恢复补给、专注成长三选一。
- 宝箱：金币或恢复补给二选一。
- 休息：恢复 HP，或增加防御与精力。
- 商店：金币购买补给、购买专注，或不消费离开；金币不足不会卡死路线。
- 事件：选择深入学习（有精力代价）或稳妥处理。

```http
GET /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/options

POST /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/options/{optionId}/choose

{
  "actionId": "幂等键"
}
```

后端校验奖励属于节点且尚未领取，然后在同一事务中写领取状态、库存或画像变化。

### 7.2 非战斗房间结算

新增独立接口：

```http
POST /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/options/{optionId}/choose

{
  "actionId": "幂等键",
  "optionId": "后端给出的合法选项"
}
```

适用于宝箱、休息、商店和随机事件。该接口不接受 `correctRate`、`cleared` 或属性增量。

不同房间的校验：

- 宝箱：只能从后端生成的宝箱选项中选择一次。
- 休息：只能选择配置允许的恢复或复习动作。
- 商店：校验商品、库存和金币余额，扣款与发放原子执行。
- 随机事件：校验事件版本和合法选项，结果由服务端规则决定。

### 7.3 事务、幂等与审计边界

1. 同一个运行先锁定 `student_tower_run`，串行化同一路线上的选择、库存和结算。
2. `actionId` 是全局幂等键；重复请求返回首次的 `result_json`，不重复扣款、发放、更新画像或解锁节点。
3. 节点选项选中、库存变化、画像变化、成长历史、动作日志与节点推进必须在同一数据库事务中完成。
4. 金币扣除前重新读取服务端画像，数量不足时整个事务失败。
5. 旧 `REWARD_PICKED/SUPPLY_USED/REST_TAKEN/SHOP_PURCHASED/TREASURE_OPENED/EVENT_RESOLVED` 通用事件不再改画像，防止绕过业务命令直接携带数值。

### 7.4 补给接口实施版

```http
GET /api/students/{studentId}/tower-run/{runId}/inventory

POST /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/inventory/{itemCode}/use
{
  "actionId": "客户端生成的幂等键"
}
```

第一版库存物品只实现 `healing_supply`：每次消耗 1 件、服务端固定恢复 30 HP。不再把金币或精力作为“使用补给”的隐式二次代价；补给成本在商店获得时结算。

## 8. 徽章闭环

不再保留接受统计参数的公开授予接口。

新增 `AchievementEvaluationService`：

```java
evaluate(String studentNo, String courseCode, String triggerType, String triggerId);
```

它只能从数据库读取：

- 正确题数和连续正确：`learning_answer_evidence`。
- 满分任务：`task_submission`、`submission_answer`。
- 节点和 Boss 通关：`student_tower_attempt`。
- 反馈与自我纠正：对应真实业务表。

`achievement` 增加稳定的 `badge_code`，并添加：

```text
UNIQUE(student_no, course_code, badge_code)
```

徽章评估失败不能回滚已经成功的答题提交；可以在主事务后同步重试，但授予必须幂等。

### 8.1 已实现结果（2026-09-02）

- 保留并复用原 `BadgeRuleEngine` 的门槛，没有让 AI 决定徽章。
- 新增稳定 `badge_code` 和 `(student_no, course_code, badge_code)` 唯一索引；启动迁移会清理旧重复徽章并映射已知旧名称。
- 正确总数、末尾连续正确、夜间答题和自我纠正均从 `learning_answer_evidence` 重新汇总。
- 满分徽章从未作废的 `task_submission` 与任务满分读取，不接受前端统计参数。
- 计时完成、有价值反馈和 Pythonic 代码风格目前没有可信结构化事实源，因此明确保持不可授予，不使用 Mock、行为日志或 AI 猜测补齐。
- 每条新答题证据提交后触发一次评估；重复触发由稳定编码和数据库唯一索引保证不会重复授予。
- 同一学生的并发徽章评估先锁定学生记录，避免两个提交同时通过“尚未获得”检查后竞争插入。

## 9. 学习行为日志边界

`POST /api/learning-logs` 只记录遥测，不触发游戏数值变化。

还需要补充：

1. 学生提交日志时，`userId` 强制取 Session，忽略请求体用户编号。
2. 教师和管理员代查日志必须按课程权限过滤。
3. AI 导师调用、资源浏览等可以写日志，但不得成为成长值事实源。
