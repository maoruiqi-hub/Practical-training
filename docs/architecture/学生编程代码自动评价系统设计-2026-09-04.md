# 学生编程代码自动评价系统设计

> 日期：2026-09-04  
> 状态：方案设计，尚未实现  
> 目标：在不依赖 Dify Workflow 的前提下，由后端直接调用模型 API 评价学生编程答案，并保留教师复核、改分和追溯能力。

## 1. 设计结论

编程题的第一版采用“题目与答案直接交给模型评价”的方式。新增题目不需要新增 Java 测试类，也不强制预先编写测试用例：

```text
学生提交代码
  → 后端校验题目与提交资格
  → 后端将题目、参考答案、评分标准和学生代码组装为固定请求
  → 直接调用模型 API 返回结构化评价
  → 后端校验模型 JSON、分数范围和评价依据
  → 保存原始代码、AI 评价和评分快照
  → 自动生成学习证据，进入知识点/能力点/成长链路
  → 教师只在异常、争议或需要改分时复核
```

教师不需要逐份批改。教师可以维护评分标准、查看 AI 评价依据、接受结果或有原因地覆盖最终成绩。AI 结果和教师结果永远分开保存。

## 2. 当前实现暴露出的缺口

当前系统已经能保存编程文本提交，但编程提交会按“待教师评阅”处理；评分事件只对在线测验中的已保存答案发布，编程提交不会进入证据投影。因此会出现：

1. 学生提交成功，但没有自动分数；
2. 没有运行记录和失败测试明细；
3. 没有生成 `learning_answer_evidence`、掌握度、能力变化和成长来源；
4. 教师手工改分与提交总分之间存在一致性风险。

本方案只补齐编程题链路，不修改已有客观题评分算法。

## 3. 第一版范围与边界

### 3.1 纳入范围

- 编程题提交、重复提交和最大尝试次数；
- 题目、参考答案、评分标准和学生代码直接发送给模型评价；
- 模型返回总分、维度分、评价依据、问题、建议和置信度；
- 后端对模型结果做 JSON Schema、分数范围和完整性校验；
- 可选的语法检查或代码运行结果作为补充事实，不要求每道题编写测试类；
- 自动结果进入教师复核页；
- 教师最终改分、填写原因、保留自动分与人工分；
- 只有“最终有效成绩”进入学习证据与成长链路；
- 幂等、审计、运行隔离和资源限制。

### 3.2 第一版明确不做

- 不调用 Dify Workflow；允许后端直接调用 DeepSeek、OpenAI 兼容接口或其他模型 API；
- 不执行学生自定义 shell、网络访问、文件系统写入或进程创建；
- 不把参考代码直接暴露给学生；
- 不使用教师逐项填写复杂参数作为评分入口；
- 不把模型结果直接视为最终成绩，低置信度或异常结果必须进入教师复核。

## 4. 评价模型

### 4.1 评分组成

每道编程题配置总分 `maxScore` 和评分标准 `rubric`。后端向模型发送固定结构：

```json
{
  "question": "题目要求",
  "referenceAnswer": "参考答案或标准解题要点",
  "rubric": [{"name":"功能正确性","maxScore":60},{"name":"算法与复杂度","maxScore":20},{"name":"代码规范","maxScore":20}],
  "studentAnswer": "学生提交的代码"
}
```

模型必须返回每个维度得分、总分、逐项依据、主要问题、修改建议和 `confidence`。后端重新计算维度分之和并限制在 `0..maxScore`，不接受模型自行修改满分或评分标准。

### 4.2 自动评价维度

自动评价只输出能由程序证实的维度：

| 维度 | 来源 | 是否影响分数 |
|---|---|---:|
| 功能正确性 | 题目、参考答案、学生代码 | 是 |
| 算法与思路 | 题目、参考答案、学生代码 | 是 |
| 边界与异常处理 | 题目要求和代码分析 | 是 |
| 代码规范 | 学生代码和评分标准 | 按评分标准决定 |
| 评价可信度 | 模型返回 + 后端完整性检查 | 决定是否复核 |

模型不得声称执行过代码或测试，除非系统确实执行并保存了执行结果。没有运行环境时，评价依据必须标记为“静态代码分析”。

### 4.3 评价状态

```text
queued → evaluating → auto_graded → accepted
                    ├→ needs_review
                    ├→ provider_timeout
                    ├→ invalid_response
                    └→ provider_error
```

模型调用、解析或校验失败不得自动给学生判 0 分，应进入“待复核”，并允许教师重新评价。

### 4.4 模型返回结构

```json
{
  "score": 82,
  "confidence": 0.78,
  "dimensions": [
    {"name":"功能正确性","score":52,"maxScore":60,"evidence":"……"},
    {"name":"算法与复杂度","score":16,"maxScore":20,"evidence":"……"},
    {"name":"代码规范","score":14,"maxScore":20,"evidence":"……"}
  ],
  "issues": ["……"],
  "suggestions": ["……"],
  "basis": "static_code_analysis"
}
```

后端以 `dimensions` 的分数之和为准，不信任模型单独返回的 `score`。`confidence` 只用于路由复核，不直接参与成绩计算。建议第一版将 `confidence < 0.70` 的结果标记为待教师复核。

## 5. 后端组件设计

### 5.1 复用现有组件

- `TaskSubmissionController`：保留提交入口和权限校验；
- `TaskSubmissionService`：提交事务、尝试次数、最终成绩和事件入口；
- `Question`：增加编程题配置引用，不改变题干和课程归属；
- `TaskQuestion`：确认题目属于当前任务，禁止客户端自行追加题目；
- `SubmissionAnswer`：保存一次编程题的学生代码、最终测试摘要和得分；
- `LearningEvidenceService`：只接收后端验证过的最终结果；
- 现有能力点映射、掌握度、成长值、画像投影服务：继续消费学习证据/评分事件。

### 5.2 新增模型评价服务

```text
CodeAssessmentService
  ├─ PromptBuilder                 组装题目、答案、评分标准
  ├─ ModelProvider                 屏蔽 DeepSeek/OpenAI 兼容 API
  ├─ StructuredAssessmentParser    JSON Schema、分数和字段校验
  ├─ ConfidencePolicy              低置信度和异常转教师复核
  └─ AssessmentResultRecorder      保存不可变 AI 评价快照
```

模型 API 只通过 `ModelProvider` 调用。API Key 只存在后端配置，不下发浏览器。模型调用设置连接超时、读取超时、重试上限和幂等键。模型不可用时保留提交，但状态为“待自动评价/待复核”，不能伪造分数。

### 5.3 可选代码执行检查

如果题目有可执行的样例或测试数据，可以额外使用隔离执行器验证代码；这是补充证据，不是新增编程题的必需步骤。后端业务代码不能调用 `Runtime.exec`、`ProcessBuilder` 或通过学生输入拼接命令。

### 5.4 执行隔离

第一版执行器使用独立 worker 进程或容器，至少满足：

- 非特权用户运行；
- 无网络；
- 只读基础运行时；
- 独立临时目录，任务结束清理；
- CPU 时间上限、墙钟超时、内存上限、输出大小上限；
- 禁止 fork、socket、危险系统调用和访问宿主业务目录；
- 业务服务只接收结构化结果，不接收执行器日志中的路径或命令。

如果部署环境暂时无法提供隔离执行器，则功能只能标记为“开发环境不可启用”，不能退化为在 Spring 进程内直接运行学生代码。

## 6. 数据模型

在现有表基础上新增以下表，字段可在 Kingbase/PostgreSQL 采用同一逻辑结构：

### `program_problem_config`

保存编程题的评价配置：

- `question_id`：唯一关联 `question`；
- `language`：第一版固定 `python3`；
- `entry_mode`：`stdin_stdout` 或 `function`；
- `time_limit_ms`、`memory_limit_mb`、`max_output_bytes`；
- `rubric_version`、`enabled`、`updated_by`、`updated_at`。

### `program_test_case`（可选）

保存可选测试用例，不是新增题目的必需条件：

- `test_case_id`、`question_id`；
- `visibility`：`sample`、`hidden`；
- `case_type`：`basic`、`boundary`、`exception`；
- `input_data`、`expected_output` 或结构化期望值；
- `weight`、`sequence_no`、`enabled`。

隐藏用例的输入和答案不能返回学生端。

### `code_evaluation_run`

保存每次代码运行的不可变快照：

- `run_id`、`submission_id`、`question_id`、`student_no`；
- `language`、`evaluator_version`、`status`；
- `provider`、`model_name`、`prompt_version`；
- `ai_score`、`confidence`、`max_score`；
- `started_at`、`finished_at`、`duration_ms`；
- `result_summary`、`failure_summary`；
- `request_hash`，用于幂等和防止同一提交被重复计分。

### `code_evaluation_case_result`（可选）

存在可执行测试用例时保存逐用例结果：

- `run_id`、`test_case_id`；
- `status`、`duration_ms`、`actual_output_preview`；
- `error_type`、`error_message_safe`、`earned_score`。

不得保存完整隐藏答案到学生可读接口；教师接口也只在确有必要时返回安全摘要。

### `submission_grade_snapshot`

保存评分版本：

- `submission_id`、`auto_score`、`final_score`；
- `source`：`auto`、`teacher_override`；
- `evaluation_run_id`、`reason`、`operator_id`、`created_at`。

该表用于解决“教师输入 80，提交结果却变成 0”这类不可追溯问题。原始提交和自动结果不覆盖，最终成绩只能由服务端根据快照产生。

## 7. 接口设计

### 学生端

```text
POST /api/submissions/{submissionId}/code-evaluation
```

仅允许提交人或系统内部调用；重复调用同一 `submissionId` 返回已有运行结果，不重复写入成长证据。

```text
GET /api/submissions/{submissionId}/code-result
```

学生可查看：最终分数、通过数量、失败类型、可公开测试结果和安全提示；不可查看隐藏输入、标准答案和内部堆栈。

### 教师端

```text
GET /api/submissions/{submissionId}/code-result/detail
PUT /api/submissions/{submissionId}/final-grade
```

教师详情可查看所有测试用例的安全结果、自动评分版本和原始代码。改分请求只接收：

```json
{
  "finalScore": 80,
  "reason": "边界条件要求与题目说明存在歧义，人工补计 10 分"
}
```

服务端校验分数范围、教师课程权限和原因非空，并写入评分快照；不得接收客户端直接修改 `status`、`autoScore` 或成长值。

## 8. 与画像和成长链路的衔接

代码评价完成后只产生一个后端可信的“已评分证据”：

```text
code_evaluation_run
  → submission_grade_snapshot(final_score)
  → SubmissionAnswer(correct/score/max_score)
  → LearningEvidenceService
  → knowledge mastery
  → 课程要点/真能力向量
  → growth_history / competency_score_history / profile projection
```

规则如下：

1. 自动评分成功后可以立即产生证据；
2. 执行器异常不产生 0 分证据；
3. 教师覆盖分数后，原自动证据标记为 superseded，按最终分数生成一条可追溯修订证据；
4. 同一 `submissionId + evaluationVersion` 只能产生一次生效证据；
5. 编程题是否影响某个知识点/真能力，必须来自题目已有的 `knowledge_point_id` 和已发布能力映射，不能由学生提交内容决定；
6. 代码风格提示第一版不影响画像，避免将不稳定的主观判断扩散到能力评分。

## 9. 教师端交互

教师看到的是抽象且可判断的结果，不需要操作执行器参数：

- 评分状态：已通过、部分通过、运行失败、待复核；
- 结果概览：自动得分 / 满分、通过测试数、主要失败类型；
- 失败标签：基础功能、边界条件、异常处理、超时、运行错误；
- 操作：接受自动结果、重新运行、覆盖最终分；
- 覆盖最终分必须填写原因；
- 页面明确区分“自动结果”和“教师最终结果”。

题目配置页只暴露“语言、运行时间、内存、测试用例权重”这类教学语义字段，并提供安全默认值；不暴露 shell 命令、容器参数等底层配置。

## 10. 分阶段实施

### 步骤一：数据与契约

输出：迁移脚本、实体、Mapper、模型 Provider 接口、评价 DTO 和提示词版本。  
效果：能保存题目评分标准、模型评价请求/响应和评分快照，每道新题只需录入题目与评分标准。

### 步骤二：模型评价链路

输出：直接调用模型 API、结构化输出校验、超时/重试/降级和低置信度策略。  
效果：学生提交后自动得到可解释的编程评价；模型异常不会伪造分数。

### 步骤三：可选执行证据

输出：对适合运行的题目增加隔离执行和样例/测试结果。  
效果：模型评价可以引用真实运行结果；没有测试配置的题目仍可正常走模型评价。

### 步骤四：复核与画像闭环

输出：教师接受/重跑/覆盖分，评分快照、证据幂等和成长链路联通。  
效果：自动分和人工分可追溯，最终结果只产生一次有效画像变化。

### 步骤五：真实账号联调与回归

输出：真实课程、真实学生、编程题、提交、自动评分、教师复核和画像记录的联调报告。  
效果：完成从学生代码到成长来源、能力变化的闭环验收。

## 11. 验收目标

### A. 自动评价正确性

1. 给定题目、参考答案、评分标准和学生代码，模型返回完整结构化评价；
2. 后端拒绝缺字段、非法 JSON、维度分超范围和总分超满分的结果；
3. 评价依据必须对应题目要求或学生代码中的可核查内容；
4. API 超时、限流、不可用或解析失败不会写入 0 分，不产生能力或成长证据；
5. 低置信度、模型与可选运行结果冲突时自动进入教师复核；
6. 自动分始终在 `0..maxScore` 范围内，维度分之和与总分一致。

### B. 安全性

1. 模型 API Key 只存在后端，学生端无法直接调用模型；
2. 学生端接口不返回参考答案、内部提示词、API 响应原文和内部堆栈；
3. 提交内容发送前过滤明显的凭据和超长内容，日志不得记录完整学生代码；
4. 若启用代码执行检查，学生代码必须满足隔离、网络禁用、超时和资源限制；
5. 题目、任务、学生和教师权限全部由服务端校验。

### C. 数据一致性与可追溯

1. 原始代码、运行结果、自动分、教师最终分均可独立查询；
2. 同一提交重复触发评价不会重复写入评分快照或成长证据；
3. 教师改分必须有原因，最终分能从评分快照复算；
4. 教师改分后，画像使用最终分，自动分仍保留；
5. 执行失败、任务版本不一致或测试配置缺失时，提交进入待复核而不是静默成功。

### D. 画像成长闭环

1. 自动评分成功后，至少生成一条与题目知识点绑定的有效学习证据；
2. 证据能触发知识掌握度更新，并在能力点映射存在时更新真能力向量；
3. 学生端能看到成长来源和能力变化，暂无数据时仍显示明确空状态；
4. 教师覆盖成绩后，变化记录包含自动分、最终分、操作人和原因；
5. 代码题没有知识点或能力映射时，只保留评分，不伪造能力变化。

### E. 最小自动化测试集

- `StructuredAssessmentParserTest`：缺字段、非法 JSON、分数封顶和维度求和；
- `ModelProviderTest`：超时、限流、重试、脱敏和幂等；
- `CodeAssessmentServiceTest`：成功、低置信度、异常、重试和幂等；
- `PythonRestrictedExecutorTest`：仅针对启用执行检查的题目，验证超时、输出、网络、文件和进程隔离；
- `FinalGradeServiceTest`：教师改分原因、权限、范围和快照；
- `LearningEvidenceIntegrationTest`：自动分、人工覆盖、重复事件和画像投影；
- 前端测试：自动结果/人工结果区分、失败状态、隐藏用例不展示、改分原因校验；
- 真实联调：学生提交一份全对代码、一份部分通过代码、一份超时代码，再完成一次教师改分，检查数据库和学生画像页面结果一致。

## 12. 第一版完成判定

只有同时满足以下条件，才认为编程自动评价第一版完成：

- 不依赖 Dify Workflow，但允许后端直接调用模型 API；
- 真实学生提交后能得到基于题目、评分标准和答案的结构化自动评价；
- 评价失败不会伪造 0 分；
- 教师可以复核并有原因地覆盖结果；
- 原始提交、自动结果、最终结果全部可追溯；
- 自动结果或最终结果能按已有设计进入学习证据、能力变化和成长来源；
- 后端自动化测试、前端测试和真实账号联调全部通过。
