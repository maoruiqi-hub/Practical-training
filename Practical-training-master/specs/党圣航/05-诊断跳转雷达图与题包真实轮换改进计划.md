# 诊断跳转、奖励页雷达图与题包真实轮换改进计划

## 1. 背景与目标

当前爬塔闭环已经接入了后端 run/node、题包接口和能力雷达接口，但实际体验仍有三个明显问题：

1. 诊断房全对后会卡一段时间才进入奖励页，用户体感像是在等待 AI 诊断回复。
2. 奖励页右侧仍展示“图谱上下文/知识点上下文”，而不是能力雷达图谱。
3. 诊断房和战斗房出现的题目仍像固定题，没有体现“数据库题库 + 每关不同 + 个性化推荐”。

本计划目标：

- 诊断全对后先跳奖励页，AI 诊断报告和能力变化说明异步补齐。
- 奖励页/结算页右侧展示能力雷达图，支持“通关前 vs 通关后”。
- 题包推荐改为真实读取数据库题库，并引入跨知识点候选池、避重、轮换和个性化排序。

## 2. 数据库题库核查结论

已实际连接当前后端配置的远程数据库并查询 `question` 表：

- `question` 总数：85 道。
- 课程分布：`course_code = 1` 共 85 道。
- 知识点分布：17 个知识点，每个知识点 5 道题。
- 每个知识点题型结构基本固定：
  - `single` 难度 1
  - `multi` 难度 2
  - `fill` 难度 3
  - `essay` 难度 4
  - `program` 难度 5

示例：

- `knowledge_point_id=3`，名称为 `Python基础语法与数据类型`，共 5 题。
- `knowledge_point_id=16`，名称为 `Web开发入门`，共 5 题。
- `knowledge_point_id=18`，名称为 `Python项目实战综合案例`，共 5 题。

由此可判断：

- 如果普通战斗房每次只从当前知识点取 5 题，那么同一个知识点必然每次都是那 5 道。
- 如果诊断房每次只从当前知识点取 3 题，并且排序固定，也会稳定抽到同一组题。
- 当前 `QuestionMapper.selectByFilter` 默认 `ORDER BY q.question_id DESC`，如果上层再 `.slice(...)` 或按固定排序选题，会进一步强化“固定前几道题”的现象。
- 如果前端没有拿到 `runId/nodeId`，或者题包接口失败，组件会回退到旧的 `getQuestionsByKnowledgePoint` 或本地 fallback 题，也会让用户看到旧题。

## 3. 问题 1：诊断全对后跳奖励页延迟

### 3.1 当前原因

当前 `FloorView.vue#handleDiagnosed` 的逻辑是：

```text
诊断完成
  -> await diagnoseTowerNode(...)
  -> 后端完成诊断节点/战斗节点
  -> 后端生成 AI 诊断报告
  -> 后端写能力变化和 AI 说明
  -> 前端收到 battleBypassed=true
  -> phase = reward
```

其中后端 `diagnoseNode` 会同步生成诊断报告，能力变化说明也可能调用 AI，所以全对之后要等接口完整返回才跳奖励页。

### 3.2 改进方案

改成“状态先行、报告后补”：

```text
最后一题答完且本地判断全对
  -> 前端立即 phase = reward
  -> 奖励页显示“诊断报告生成中”
  -> 后台继续调用 diagnoseTowerNode
  -> 后端立即完成节点状态和解锁
  -> AI 报告慢慢生成
  -> 返回后刷新右侧诊断结果/能力雷达
```

### 3.3 前端实施

修改文件：

- `frontend/src/views/FloorView.vue`
- `frontend/src/components/RewardDraft.vue`

具体改法：

1. 在 `handleDiagnosed(result)` 中，如果 `result.status === 'mastered'` 且 `correctRate === 1`：
   - 先设置：
     ```js
     battleResult.value = {
       cleared: true,
       correctRate: result.correctRate,
       diagnosisBypass: true,
       pendingDiagnosisReport: true
     }
     phase.value = 'reward'
     ```
   - 不再等待 `diagnoseTowerNode` 返回后才跳转。

2. 异步调用 `diagnoseTowerNode`：
   - 成功后更新：
     - `diagnosisResult.report`
     - `battleResult.pendingDiagnosisReport = false`
     - `run/node` 状态
     - 能力雷达数据
   - 失败时：
     - 奖励页保留
     - 显示“诊断同步失败，可返回地图后刷新重试”
     - 不阻塞奖励页。

3. 奖励页/右侧诊断结果区域增加 loading 状态：
   - `pendingDiagnosisReport = true` 时显示骨架屏或 `诊断报告生成中...`
   - 报告返回后替换为 AI 诊断摘要。

### 3.4 后端实施

优先做前端先跳转即可；如果还慢，再做后端拆分：

修改文件：

- `backend/src/main/java/com/neu/CoursePlatform/service/impl/TowerRunServiceImpl.java`

可选后端优化：

1. `diagnoseNode` 先完成：
   - 诊断节点 `cleared`
   - 绑定战斗节点 `cleared`
   - 解锁后继节点
   - 写 attempt
   - 写基础 ability delta

2. AI 诊断报告改为异步生成：
   - 先返回 `reportStatus = generating`
   - 后台生成后更新 `student_tower_attempt.ai_report_json`
   - 新增查询接口：
     ```http
     GET /api/students/{studentId}/tower-run/{runId}/nodes/{nodeId}/diagnosis-report
     ```

## 4. 问题 2：奖励页展示能力雷达图谱

### 4.1 当前原因

奖励/结算阶段右侧仍复用了 `KnowledgeContextPanel`，因此显示的是：

- 当前知识点
- 前置知识点
- 后继知识点
- 相关知识点

这不是用户想看的“能力雷达图谱”。

### 4.2 改进方案

新增一个紧凑型能力雷达组件，在奖励页和结算页展示：

```text
AbilityRadarChart.vue
  -> 调用 getAbilityRadar(studentId, courseId, runId, nodeId)
  -> ECharts radar
  -> 两条线：通关前 / 通关后
  -> 下方展示变化最大的能力点和 AI/规则说明
```

### 4.3 前端实施

新增文件：

- `frontend/src/components/AbilityRadarChart.vue`

复用 API：

- `frontend/src/api/index.js#getAbilityRadar`

修改文件：

- `frontend/src/views/FloorView.vue`
- `frontend/src/components/RewardDraft.vue`，如需要把雷达放入奖励组件内部。

具体逻辑：

1. 当 `phase === 'reward' || phase === 'settlement'`：
   - 右侧不显示 `KnowledgeContextPanel`
   - 改显示 `AbilityRadarChart`

2. `AbilityRadarChart` props：

3. pending 时展示：

2. 如果诊断报告异步生成中，雷达接口不等待 AI。
3. `dimensions` 中增加：

   - `sourceNodeName`

## 5. 问题 3：题目仍然像固定题

### 5.1 当前原因

当前题包推荐虽然已经读数据库，但候选池仍偏窄：

```text
优先按当前 knowledgePointId 取题
如果数量 >= targetCount，就不会扩展到其他知识点
```

而数据库每个知识点刚好只有 5 道题：

- 普通战斗 `targetCount = 5`，会拿完当前知识点全部 5 题。
- 诊断 `targetCount = 3`，如果排序稳定，会重复拿同样 3 题。
- 题包一旦缓存到 `student_tower_question_pack`，重复进同一节点会继续使用同一题包。

所以“每关不一样”不能只靠当前知识点题库，必须扩大候选池并引入轮换机制。

### 5.2 新题包策略

题包候选池改成四层：

```text
第 1 层：当前节点主知识点题目
第 2 层：当前知识点的前置/后继知识点题目
第 3 层：同能力点绑定的其他知识点题目
第 4 层：本 run 已出现过的知识点题目，用于 Boss/综合复习
```

不同房间使用不同配比：

#### 诊断房 3 题

```text
2 题：当前知识点
1 题：前置知识点或同能力点弱项
```

题型优先：

- `single`
- `fill`
- `multi`

诊断不优先出 `essay/program`，避免全对判断不稳定。

#### 普通战斗 5 题

```text
3 题：当前知识点
1 题：前置或后继知识点
1 题：同能力点弱项
```

题型覆盖：

- 低难度节点：single/multi/fill 为主。
- 中难度节点：加入 essay。
- 高难度节点：加入 program。

#### 精英战 6 题

```text
3 题：当前知识点
2 题：同能力点弱项
1 题：历史错题关联知识点
```

#### Boss 8 题

```text
覆盖本 run 中出现过的多个知识点
优先薄弱知识点和最近错题
避免单一知识点占比超过 40%
```

### 5.3 避重与轮换机制

新增或强化使用记录：

方案 A：先复用已有表，低成本实现。

- 从 `student_tower_question_pack.question_ids_json` 查询当前 run 已用过的题。
- 从 `student_tower_attempt.answer_summary_json` 查询最近已答过的题。
- 推荐时降低这些题的权重。

方案 B：新增题目使用表，后续更稳。

```sql
CREATE TABLE IF NOT EXISTS student_question_usage (
    id VARCHAR(64) PRIMARY KEY,
    student_no VARCHAR(64) NOT NULL,
    course_code VARCHAR(64) NOT NULL,
    run_id VARCHAR(64),
    node_id VARCHAR(64),
    question_id VARCHAR(64) NOT NULL,
    knowledge_point_id VARCHAR(64),
    correct BOOLEAN,
    source VARCHAR(32),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

第一阶段建议用方案 A，减少表变更。

### 5.4 后端实施

修改文件：

- `backend/src/main/java/com/neu/CoursePlatform/service/impl/TowerQuestionPackServiceImpl.java`
- `backend/src/main/java/com/neu/CoursePlatform/mapper/QuestionMapper.java`
- `backend/src/main/resources/mapper/module3_assessment/QuestionMapper.xml`

核心改动：

1. 增加候选池收集方法：

```java
private List<Question> collectCandidates(StudentTowerRun run, StudentTowerNode node, String mode)
```

内部收集：

- 当前知识点题。
- `knowledge_relation` 中前置/后继题。
- `ability_knowledge_point` 中同能力点题。
- 当前 run 所有 node 涉及的知识点题。

2. 增加配额选择方法：

```java
private List<Question> selectByQuota(
    List<Question> main,
    List<Question> related,
    List<Question> weak,
    List<Question> runScope,
    QuestionPackPolicy policy
)
```

3. 增加避重：

```java
Set<String> usedInRun = usedQuestionIdsInRun(runId);
Set<String> recentUsed = recentUsedQuestionIds(studentNo, courseCode);
```

评分中：

```text
未用过 +30
本 run 已用过 -40
最近答过 -25
当前知识点 +35
相关知识点 +15
符合目标难度 +20
符合题型配额 +15
```

4. 题不足时才允许重复：

```text
第一轮：严格避重
第二轮：允许最近用过但降低权重
第三轮：题库不足才重复当前知识点题
```

5. 题包缓存规则调整：

当前 `getOrCreateQuestionPack` 找到已有 pack 就直接返回。需要改成：

- 同一 `nodeId + mode` 第一次进入：返回已有 pack，保证刷新不变。
- 如果节点已通关后再次复盘：返回旧 pack。
- 如果节点失败后重试：允许生成 `attemptRound + 1` 新题包，避免重试还是同题。
- 可在 `strategy_json` 中记录 `round`。

修改文件：

- `frontend/src/components/BattleRoom.vue`

改动：

2. 题包接口失败时，不静默回退旧题，而是显示：

   - 方便发现问题。
3. 在题目区域显示小标签：

   - `题包ID`

这样一眼能确认是不是已经进入新题包逻辑。

### 5.6 验收标准

1. 在数据库中，当前课程仍只有每知识点 5 题时：
   - 普通战斗不再固定只拿当前知识点 5 题。
   - 至少混入 1 到 2 道前置/后继/同能力点题。

2. 同一个学生连续进入不同节点：
   - 题目组合不同。
   - 题包 ID 不同。
   - 题目来源能在界面或日志中确认。

3. 同一节点刷新页面：
   - 当前未完成 attempt 的题包保持不变。
   - 避免刷新换题导致不公平。

4. 节点失败后重试：
   - 可以换一组题。
   - 但仍围绕相同知识点和能力点。

5. Boss：
   - 覆盖多个知识点。
   - 不出现 8 题都来自同一知识点。

## 6. 推荐实施顺序

### 阶段 1：立即改善体验

1. `FloorView.vue` 诊断全对先切 `phase='reward'`。
2. 奖励页诊断结果显示 loading。
3. `RewardDraft` 或右侧面板改为显示 `AbilityRadarChart`。

### 阶段 2：修正题包逻辑

1. `TowerQuestionPackServiceImpl` 增加跨知识点候选池。
2. 增加本 run 已用题避重。
3. 增加题型/知识点配额。
4. 前端显示题包来源，防止误以为还在用旧题。

### 阶段 3：后端异步 AI

1. `diagnoseNode` 不同步等待 AI 诊断报告。
2. 诊断报告和能力解释后台生成。
3. 前端轮询或下一次刷新时补齐报告。

## 8. 最小可展示验收路径

1. 进入诊断房。
2. 答对全部诊断题。
3. 页面立即进入奖励页。
4. 奖励页右侧显示能力雷达 loading。
5. 后端诊断接口返回后，能力雷达显示通关前/通关后对比。
6. 返回地图进入下一个战斗节点。
7. 战斗房题目与上一关不同。
8. 控制台或页面能看到题包 ID 和数据库推荐来源。

## 9. 风险与注意点

- 当前题库每个知识点只有 5 道，如果要求“同一知识点每次完全不同”，数据库题量不足，必须混入关联知识点题，或者继续扩充题库。
- 编程题和简答题自动判分不稳定，诊断房不应优先使用。
- 前端不能静默回退本地 fallback，否则会掩盖题包接口问题。
- AI 报告不能阻塞跳转；报告慢是可接受的，页面卡住不可接受。
- 题包刷新策略要兼顾公平：未完成时刷新不能换题，失败重试可以换题。
